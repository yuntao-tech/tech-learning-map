3.3 持续交付 vs 持续部署 用「有没有人工闸门」区分了两个术语，但没有打开流水线本身。本节打开它： 它由哪几个阶段组成，每个阶段拦什么、给谁反馈、该花多长时间， 以及让整条通道成立的两条铁律 —— 制品只构建一次、任一阶段失败即停。 换个角度说，部署流水线就是 4.6 价值流映射 画出来的那张图的可执行版本：图上的每一个环节，在这里都变成了一段真的会跑、会红、会拦人的代码。

kp-6-2-1

部署流水线Deployment Pipeline

⭐ 考纲核心📌 高频
① 是什么

部署流水线 Deployment pipeline 是把一次代码提交自动送到可上生产的制品乃至生产环境的一条 自动化通道：它由若干个前后依赖的阶段组成，每个阶段都是一道有明确通过标准的验证关卡， 制品只能从左往右单向前进，任何一关没过就地停下。

三个构成要件说明
有序的阶段不是一堆并列的任务，而是一条有先后的链条。后一阶段的输入，是前一阶段验证通过的产物
每阶段有通过标准通过标准写在流水线里，是可执行的判断，不是写在文档里等人去看。「绿」和「红」都由机器给出
唯一的上生产路径生产环境只接受来自流水线的制品。绕过流水线的手工上线，等于这条流水线不存在

Deployment pipeline 逐字列于 DOFD v3.4 官方考纲术语表（Concept and Terminology List）； 上面这条中文释义与三个构成要件为本站措辞与教学整理。

② 为什么存在 · 解决什么问题

它要消灭的是一段具体的黑暗时间：代码合进主干之后、有人真正验证它之前的那一段「无人知晓区」。

  • 一个 40 人的团队，测试集中在发布前两周做。开发者提交完就转下一个任务， 至于这次提交有没有把别人的东西弄坏，要等六周后的集中回归才知道。
  • 回归第一天发现三个模块互不兼容，追溯到六周前的一次提交。那位作者已经换了项目， 要重新读懂六周前的上下文才能改 —— 同一个缺陷，六周后的修复成本是当时的十几倍。
  • 更隐蔽的一层：上线动作本身是不可复现的。谁在什么时候手工改了哪台机器的哪个配置， 没有记录。出事时先花两小时争论「预发和生产到底哪里不一样」。

部署流水线用两个动作切断它：把「这次提交能不能用」的答案压缩到分钟级， 并把上生产的全部步骤收进同一条可重复、可审计的路径。 提交之后不再有黑暗时间 —— 每一次提交都立刻得到一个二值答案。

本案例为本站构造的教学示例，数字用于说明机制，非真实调研数据。

③ 与相邻概念的区别
对比对象部署流水线它
持续交付 Continuous Delivery 是被依赖的机制 / 资产：一条具体存在、可以画出来的通道 是一种实践 / 组织能力：随时处于可发布状态。它依赖流水线，但不等于流水线（见 3.3）
持续集成 Continuous Integration 覆盖从提交一直到生产的全程 只覆盖流水线最左边那几段：合并、构建、自动化测试。它是流水线的一部分，不是全部（见 3.2）
DevOps 工具链 DevOps toolchain 是一条有顺序的通道：讲的是「先做什么、后做什么、哪里能拦下来」 是一组工具的集合：讲的是「用什么做」。同一条流水线可以换掉全部工具而结构不变（工具链见本章 6.5 DevOps 工具链架构）
价值流映射 Value stream mapping 是会跑的那一版：每个环节都是真在执行的代码 是画在纸上的那一版：用来看清等待与浪费在哪（见 4.6）。两者描述同一条价值流，一个用来看，一个用来跑

最容易混的一点：部署流水线是机制，持续交付是实践。 考题里只要出现「依赖部署流水线来实现……」，就说明流水线是题干给出的条件， 答案要落在实践名上，不可能是「部署流水线」自己。

本对照表的四组维度为本站教学整理，官方未以此形式给出对照； 表中 Deployment pipeline、Continuous delivery、Continuous integration、 DevOps toolchain、Value stream mapping 五个词条均列于 DOFD v3.4 官方考纲术语表。

④ 工程中怎么用

判断一条流水线是不是真的成立，看四件事：

  • 一次提交 = 一个流水线实例：能指着任何一个制品，说清它来自哪一次提交、过了哪几关。 做不到这一点，就无法回答「生产上跑的到底是哪份代码」。
  • 流水线定义与代码同仓库：流水线本身是版本化的文件，跟着代码一起评审、一起回滚。 流水线配置存在某个界面里、只有两个人会改，它就成了新的单点故障 SPOF。
  • 把手工步骤一个一个吃进来：改造顺序不是从最难的开始，而是从 最频繁、最容易出错的那一步开始。每吃掉一步，发布手册就短一页。
  • 先画后建：建流水线之前，先照 4.6 价值流映射 把现状画一遍。图上等待时间最长的那一段，才是流水线第一版最该覆盖的地方 —— 否则很容易把已经很快的环节自动化得更快，而排队的地方一动没动。

以上四条检查动作为本站教学整理，官方文件把 Deployment pipeline 列为术语，未规定实施清单。 Single Point of Failure (SPOF) 列于 DOFD v3.4 官方考纲术语表。

⑤ 考试怎么考
  • 官方已确认的一条：依赖部署流水线实现「按需一键部署」的实践，答案是持续交付 —— 由 DOFD v3.4 官方样题答案键确认。 这条题的价值不在答案本身，而在它示范了一种句式：把「部署流水线」放在题干里当条件，问你这叫什么实践。
  • 干扰项长什么样： 「部署流水线」自己（题干已经把它说出来了，再选它等于原地打转，这是本节最典型的一个陷阱）、 持续集成（它不覆盖到生产）、 DevOps 工具链（那是工具的集合，回答的是「用什么」而不是「什么实践」）。
  • 另一种角度：问流水线里有什么。这里有两条官方事实可以直接当判据： 持续集成的必要前提是自动化的单元、集成与验收测试； 自动部署每个通过单元、集成、用户验收与非功能测试的版本属于持续部署 —— 两条均由 DOFD v3.4 官方样题答案键确认。 注意两份清单不一样：非功能测试出现在后一条里，不在持续集成的前提里。
  • 排除技巧：先判断题干问的是「叫什么」还是「用什么」。 问「这属于哪种实践」，答案一定是一个实践名（持续集成 / 持续交付 / 持续部署）； 问「哪些属于工具链要素」，答案才落在工具那一侧。

以上仅描述命题角度与干扰项构造方式，不复制任何官方样题的题干与选项原文； 官方未公布命题规律与题型分布，句式分析与排除技巧为本站教学推断。

⑥ 记忆要点

从提交到生产只有这一条路，路上每一关都能把它拦下来。

配一句区分：流水线是「路」，持续交付是「随时能走这条路」的能力。 题干给了路，问的就一定是能力。

流水线的分层结构与十分钟规则Pipeline Stages & the Ten-Minute Commit Stage

📝 教学整理 🧭 延伸 · 非考纲 📌 高频
① 是什么

分层的意思是：不同种类的验证按「快慢 / 贵贱 / 离真实生产多远」排成前后几段， 而不是一股脑塞进一个巨大的测试任务里。典型的五段如下（对应图 6-2-1）：

阶段拦什么典型时长失败意味着
提交阶段
Commit stage		 编译错误、单元测试失败、静态扫描告警。产出本次唯一的那个制品 5–10 分钟 提交者本人立刻改，通常几分钟能定位 —— 他脑子里还装着刚写的代码
验收阶段
Acceptance stage		 把制品部署到类生产环境，跑集成测试与自动化验收测试：模块之间、系统与外部依赖之间是否还对得上 30–90 分钟 问题在「组合」而不在「单件」，需要开发团队一起看
非功能测试
Non-functional		 功能对了但撑不撑得住：性能、容量、负载、安全扫描、故障韧性 1 小时起 往往要改设计而不是改代码，反馈落在架构与安全侧
手工验证 / UAT
可选		 机器判断不了的部分：探索式测试、业务方确认、体验判断 小时 – 天 整段可以不存在。它是唯一一段「没有也能成立」的阶段
生产部署
Production deploy		 不再是「测试」，而是把已经验证过的那个制品装上去，并靠遥测确认它没变坏 分钟级 触发一键回滚或前滚；反馈来自真实用户
这套五段划分、阶段命名与典型时长为本站教学整理，DOFD 官方文件未给出流水线的阶段结构表。 可以引为官方的是两点：Deployment pipeline 与 Testing (unit, acceptance, integration) 均列于 DOFD v3.4 官方考纲术语表； DOFD v3.4 官方样题答案键确认的一条判断中， 单元、集成、用户验收、非功能四类测试是并列出现的 —— 这与上表把它们分到不同阶段的做法一致。
② 为什么存在 · 解决什么问题

分层要解决的痛点，出现在一个团队已经把测试全自动化之后： 测试都在，但一次跑完要 78 分钟，于是它们几乎没起作用。

  • 某团队把 4 200 个测试放进同一个任务，提交后 78 分钟出结果。 开发者不会坐等 —— 他去干别的了。78 分钟后回来，他已经又提交了 3 次， 红灯到底是哪一次引起的，得先花时间二分。
  • 更糟的是行为上的适应：既然反正要等一个多小时，不如攒够几个改动一起提交。 批量重新变大，冲突变多，定位更难 —— 第 2 章 第一步 · 流动（2.2） 要求的小批量与快速流动，被一个技术细节原样抵消掉了。
  • 分层之后：编译与单元测试留在提交阶段，6 分钟给出答案； 慢的集成、验收、性能测试推到后面的阶段异步跑。 开发者拿到的是一个「值得等」的快答案，攒批的动机随之消失。

这就是十分钟规则：提交阶段一旦超过十分钟，人的行为就会变 —— 开始切换上下文、开始攒批、开始把红灯当背景噪音。 反馈的价值与它到达的延迟成反比，这条曲线在十分钟附近掉得最陡。

本案例为本站构造的教学示例，数字用于说明机制，非真实调研数据； 「十分钟」这一阈值属持续交付领域的通行经验做法，属延伸补充，不在 DOFD 考纲术语表与官方文件内。

③ 与相邻概念的区别
维度提交阶段验收阶段非功能测试手工验证 / UAT
回答的问题 这段代码本身对不对 拼在一起还对不对 撑不撑得住、安不安全 人看着满不满意
由谁执行 机器 机器 机器 人
能不能没有 不能 不能 不能 可以，整段省略
失败反馈给谁 提交者本人 开发团队 架构与安全 业务与产品
环境 构建机 类生产环境 接近生产规格 预发 / 演示环境

最容易混的一点：「验收测试」与「用户验收测试 UAT」要分两层看，不能靠缩写一刀切。
第一层，验收测试 acceptance testing 在流水线语境下指自动化验收测试，由机器在验收阶段跑； 它对应官方术语 Testing (unit, acceptance, integration) 中的 acceptance —— 官方术语表只列词条、不附定义，官方并未界定该 acceptance 的执行方式，此处的「自动化」定性为本站教学整理。
第二层，用户验收测试 UAT 有两种落法。 一种是把用户场景用例做进自动化验收套件，由流水线自动执行 —— DOFD v3.4 官方样题答案键确认的那条持续部署判断里说的就是这一种，因为全自动部署不可能停下来等人； 另一种才是本节图 6-2-1 里由人做的探索式测试与业务确认，只有这一段是可选的。
判据不看缩写，看这道关卡是不是流水线自动执行的闸门：是 → 属自动化验收；不是 → 属可选的人工确认。 上面这一层拆分的依据，是官方样题答案键中「验收测试」与「用户验收测试」分列出现这一事实；推论本身为本站教学整理。

本对照表的五个维度、「谁执行」与「能不能没有」两行判据，均为本站教学整理，官方未以此形式给出阶段对照。

④ 工程中怎么用

切分阶段时，四条可操作的规则：

  • 按失败原因切，不按工具切：同一个阶段里的检查，失败之后应该由同一群人、 用同一种思路去修。把「单元测试」和「性能测试」放一起，等于让两拨人抢同一个红灯。
  • 让坏消息先到：阶段内部也要排序 —— 最快、最可能失败的检查放最前面。 一次编译错误没必要等 800 个测试跑完才被发现。
  • 守住十分钟：提交阶段一旦超过十分钟，要动的是测试的位置而不是测试的数量： 把慢测试挪到验收阶段、并行执行、按变更范围裁剪，而不是删掉它们。
  • 每个阶段都能单独重跑：验收阶段挂了，不需要从编译重来一遍。 做不到这一点的流水线，每次排查都要付一遍全程的时间成本。

以上四条切分规则为本站教学整理，官方文件未规定阶段划分方法。

⑤ 考试怎么考
  • 能当硬判据用的两条官方事实：持续集成的必要前提是 自动化的单元、集成与验收测试； 自动部署每个通过单元、集成、用户验收与非功能测试的版本属于持续部署 —— 两条均由 DOFD v3.4 官方样题答案键确认。 把两份清单叠起来看，就是流水线里测试的层次顺序。
  • 最典型的干扰项：把非功能测试塞进持续集成的前提里。 读起来很顺（性能测试当然也是自动化测试），但官方确认的那条前提清单里没有它。 同理，把「用户验收测试 UAT」写成持续集成的前提也是错的方向。
  • 第二种干扰项：颠倒快慢顺序。选项描述成「先跑性能与安全测试，通过后再跑单元测试」。 判据很简单：贵的检查不会排在便宜的检查前面，否则每次都要为一个编译错误付几小时。
  • 排除技巧：遇到测试类型排序题，按「范围从窄到宽、时间从短到长」排一遍 —— 单元 → 集成 → 验收 → 非功能 → 人工确认。与这条顺序相反的选项基本都可以划掉。 限定条件：这条顺序是本站按「范围从窄到宽」整理的教学顺序， 遇到逐字复述官方测试清单（单元、集成、用户验收、非功能）的选项时不适用 —— 那是官方措辞，不能拿本站顺序去否定它。

以上仅描述命题角度与干扰项构造方式，不复制任何官方样题的题干与选项原文； 官方未公布命题规律与题型分布，干扰项分析与排除技巧为本站教学推断。

⑥ 记忆要点

快的先跑，贵的后跑；提交阶段十分钟内必须给出答案。

五段口诀：编译单测 → 集成验收 → 性能安全 → 人看一眼（可选）→ 上生产。 越往右越慢、越贵、越像真的生产环境。

两条铁律：制品只构建一次 · 失败即停Build Once, Deploy Many & Fail Fast

📝 教学整理 🧭 延伸 · 非考纲 ⚠️ 易混淆
① 是什么

这两条约束不改变流水线的形状，但决定它是否可信：

铁律内容
制品只构建一次
build once, deploy many		 编译打包只在提交阶段发生一次，产出一个带固定版本与校验和的二进制。 此后测试环境、类生产环境、生产环境部署的，都是同一个文件。 环境之间的差异只通过外部配置注入，不通过重新构建体现
失败即停
fail fast		 任一阶段没通过，这个制品就地停下，不进入下一阶段。 没有「先放过去，后面再补」，也没有「这个测试老是偶发失败，标成允许失败」

这两条表述为本站教学整理，属持续交付领域的通行原则， DOFD 官方文件未以「铁律」或此措辞给出。可引为官方的是 Deployment pipeline 这一术语本身， 以及 PeopleCert DevOps Foundation Blueprint 中 Principles & Practices 一栏的逐字表述 —— 频繁的小批量发布「reduce lead time, costs and risks」， 这两条铁律正是对其中 risks 的直接回应。

② 为什么存在 · 解决什么问题

铁律一的痛点：预发全绿，生产炸了。

  • 某团队的流水线在每个环境各自执行一次构建，理由听起来很正当： 「这样能保证构建出来的东西跟该环境匹配」。
  • 某次上线，预发全部通过，生产启动即失败。查了 5 个小时， 原因是生产构建机上一个传递依赖被解析成了另一个小版本 —— 预发验证过的那个二进制，和生产上跑的那个，压根不是同一个东西。
  • 本质问题：每个环境各自构建，等于每次上生产都在部署一个从来没被测试碰过的制品。 前面所有阶段的验证结论，对生产上的那个文件一条都不成立。

铁律二的痛点：破窗。

  • 一个测试偶发失败，团队为了不挡住发布，把它标成「允许失败」。第二个月又标了 6 个。
  • 三个月后，那条流水线的红灯没人再看 —— 因为红灯已经不代表任何东西。 一旦允许带病往下走，验证关卡就退化成了一排装饰。
  • 失败即停真正保护的不是这一次发布，而是「绿灯意味着可以上生产」这个信念。 这个信念一旦破产，重建的成本远高于当初停下来修那一次。

以上两个案例为本站构造的教学示例，数字用于说明机制，非真实调研数据。

③ 与相邻概念的区别
对比对象铁律的说法常见的误读
制品只构建一次 只构建一次，然后部署很多次。部署次数越多越好 误读成「只部署一次」。两者毫无关系 —— 同一个制品可能被部署到几十个环境、上百次
环境差异怎么处理 通过外部配置注入：连接串、开关、资源规格从环境读取 误读成「所以不能有环境差异」。差异当然存在，只是不能靠重新编译来体现
失败即停 停的是这一个制品的前进：它不进下一阶段 误读成「整条流水线停摆、所有人不许提交」。别的提交仍然可以跑自己的流水线实例
失败即停 vs 自动重试 红灯要被看见并修掉 误读成「加个自动重试就不算失败了」。重试掩盖的是不稳定， 它让红灯失去含义，正是破窗的第一步

最容易混的一点：「构建一次」限制的是编译打包，不是部署。 正好相反 —— 正因为只构建一次，同一个制品才能被放心地反复部署， 部署频率 Deployment frequency才可能提上去。 把这条铁律记成「少部署」，方向刚好反了。

本对照表的四组「说法 vs 误读」为本站教学整理，官方未以此形式给出； Deployment frequency 列于 DOFD v3.4 官方考纲术语表。

④ 工程中怎么用
  • 建一个制品仓库，版本号不可变：制品带唯一版本与校验和， 一旦发布就不允许覆盖。「同名不同内容」是这条铁律最常见的破法。
  • 让制品可追溯到提交：任何一个在生产上跑的制品， 都能回答「来自哪次提交、过了哪几个阶段、谁批的」。这也是审计要的东西。
  • 配置与制品分离：配置文件不进制品包。 判据很简单 —— 换环境时如果需要重新打包，就说明配置进包了。
  • 红灯优先于新功能：流水线红着的时候，修它的优先级高于写新代码。 这是「失败即停」在人身上的那一半，只靠工具落实不了。
  • 不稳定测试要隔离，不要忽略：把它移出主路径单独治理并限期修复， 而不是永久标成「允许失败」。两者的区别是有没有截止日期。

以上五条落地动作为本站教学整理，官方文件未规定实施方式。

⑤ 考试怎么考
  • 命题角度：问部署流水线的特征。这两条铁律不是官方逐字条目， 但它们是描述流水线时最常出现的正确表述，选项里通常以 「各环境部署同一个制品」「某阶段失败则不再继续」这样的句式出现。
  • 最像对的干扰项：「为每个环境分别构建，以确保与该环境匹配」。 它读起来非常合理，甚至像是严谨的做法 —— 但它恰恰取消了前面所有测试的效力。 见到「分别构建 / 各自编译 / per-environment build」这类措辞，直接划掉。
  • 第二种干扰项：「失败的阶段可以跳过，等发布后再修复」。 凡是允许带病继续的选项，在这一组题里都是错的方向。
  • 排除技巧：把每个选项代入一句反问 —— 「按这个做法，上生产的那个东西被测过吗？红灯还有意义吗？」 两个答案里只要有一个是「否」，这个选项就不是流水线的正确描述。
  • 与 3.3 的联动：题干若同时出现流水线与「按需一键部署」， 答案落在持续交付（由 DOFD v3.4 官方样题答案键确认）， 别被本节的铁律带偏去选「部署流水线」。

除明确标注「官方样题答案键确认」的一条外， 以上命题角度、干扰项分析与排除技巧均为本站教学推断，官方未公布命题规律； 以上不复制任何官方样题的题干与选项原文。

⑥ 记忆要点

构建一次，处处部署；一处失败，就地停下。

反问式自检：「生产上跑的那个文件，被前面哪个阶段测过？」 答不上来，就说明这条流水线违反了第一条铁律。

⭐ 一分钟回忆清单
  • 定义：Deployment pipeline 是从一次提交到生产之间唯一的那条自动化通道， 由前后依赖、各有通过标准的阶段组成（Deployment pipeline 列于 DOFD v3.4 官方考纲术语表）
  • 五段结构：提交阶段（编译 · 单元 · 静态扫描）→ 验收阶段（集成 · 自动化验收）→ 非功能测试（性能 · 安全）→ 手工验证 / UAT（可选）→ 生产部署（本站教学整理的阶段划分）
  • 铁律一：制品只构建一次，各环境部署同一个二进制，差异只靠配置注入。 每环境各自构建 = 每次上生产都在部署一个从没被测过的东西
  • 铁律二：任一阶段失败即停，不允许带病往下走。放过一次，红灯就少一分含义
    （两条铁律的措辞与「铁律」这一提法为本站教学整理，官方未以此形式给出）
  • 十分钟规则：提交阶段超过十分钟，开发者开始攒批与切换上下文， 第一步 · 流动（2.2）被破坏（阈值为本站教学整理）
  • 官方确认（DOFD v3.4 官方样题答案键）：依赖部署流水线实现按需一键部署 → 持续交付； 持续集成的必要前提是自动化的单元、集成与验收测试； 自动部署每个通过单元、集成、用户验收与非功能测试的版本 → 持续部署
    （官方确认的那份持续集成前提清单中未列入非功能测试；由此推出「CI 前提不含非功能测试」是本站教学推断）
  • 别混：流水线是机制，持续交付是实践； 流水线是有序通道，工具链是工具集合； 流水线是价值流映射的可执行版本（4.6）
