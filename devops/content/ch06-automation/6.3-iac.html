6.3 基础设施即代码

Infrastructure as Code
📘 官方模块子项 ⚠️ 易混淆

自动化流水线可以把代码构建、测试、部署得毫无差错， 然后把它装到一台没人说得清是怎么变成今天这样的服务器上。 基础设施即代码 Infrastructure as Code / IaC 处理的正是这一段： 把「环境应该长什么样」写成版本控制中的声明式代码，环境由代码生成，而不是由人手工点出来。 它要杀死的敌人只有一个 —— 配置漂移。

🎯 本节要回答
  • 配置漂移是怎么在没有任何人犯错的情况下积累出来的，IaC 从哪一刀切断它
  • 声明式与命令式的分界到底在哪里，为什么幂等性是 IaC 的关键属性而不是附带好处
  • 基础设施变成代码之后，具体获得了哪四项原本只属于应用代码的能力
kp-6-3-1

基础设施即代码Infrastructure as Code / IaC

📘 官方模块子项 📌 高频
① 是什么

基础设施即代码 Infrastructure as Code / IaC 是用版本控制中的声明式代码来定义和创建基础设施的实践： 服务器、网络、负载均衡器、数据库实例、权限策略应该处于什么状态， 全部写成文件，由工具读取这些文件把环境生成出来 —— 而不是有人登录控制台点一遍，或者跑一份只能用一次的脚本。

三个要件缺了它就不算 IaC
写成代码环境的定义是文本文件，可以被 diff、被搜索、被复制。控制台上的点击留不下任何可比对的东西
放进版本控制和应用代码一样有提交历史、作者、评审记录。「谁在什么时候为什么改了这台机器」有唯一答案
声明目标状态描述的是「环境要成为什么样」，不是「先做这步再做那步」。这一条是下一个知识点的全部内容
档位说明：Infrastructure as Code 不在 DOFD v3.4 官方考纲术语表（Concept and Terminology List）的 67 条内， 也不是 v3.4 课程大纲 M6 的具名子项，因此不标「⭐ 考纲核心」； 但它逐字出现在 PeopleCert DevOps Foundation Blueprint 的 CALMS-A 描述句里 —— “CI/CD toolchains, and infrastructure-as-code enable automation, consistency, velocity and fast recovery.” —— 属官方文件正文点名的内容，因此本节判 📘 官方模块子项，不判「🧭 延伸 · 非考纲」。 上表「三个要件」的拆法是本站教学整理，官方未给出 IaC 的定义句。
② 为什么存在 · 解决什么问题

它解决的痛点有一个专门的名字：配置漂移。 漂移的可怕之处在于 —— 它不需要任何人犯错就会发生。

  • 某支付网关有三台 web 服务器，上线那天照同一份 21 步安装手册装出来，完全一致。 半年里发生了五件事：排障时在 web-01 上装了个抓包工具；一次促销前手工把 web-01 的连接数上限调大； 一次线上热修复直接改了 web-02 的配置文件；一个安全补丁在 web-02 上打了、另外两台漏了； web-03 某次重启后有个辅助进程没起来，没人发现。 五件事没有一件是错误操作，但半年后这三台机器已经是三台不同的机器。
  • 账单在故障那天到达：某个请求只在特定机器上超时，在测试环境永远复现不出来； 排查花了 4 小时 20 分，最后发现是 web-01 那次手工调大的连接数与新版本的连接池配置冲突。 而当初调这个数的人已经离职，没有任何一条记录说明它为什么被改成那个值。
  • 回滚同样卡住：要把环境退回到「上周那个能用的样子」， 但「上周那个样子」不存在于任何地方 —— 只存在于三台机器当时的磁盘上，而磁盘已经被改过了。

IaC 的介入点不是「让人别手工改」，那是纪律要求，纪律会失效。 它是结构性的：把环境的唯一权威定义搬进代码仓库， 环境每次都从这份定义重新生成或收敛回去。 于是手工改动不再是「不该做的事」，而是「做了也留不住的事」 —— 想让改动活下来，只能改代码。

本案例与其中的数字为本站构造的教学示例，用于说明漂移的累积机制，非真实调研数据。

③ 与相邻概念的区别
对比对象基础设施即代码它
手工搭建 + 运行手册 定义在仓库里，执行者是工具。手册的内容变成了可执行的文件 定义在文档里，执行者是人。文档会过期，而没人知道它什么时候过期的
一次性安装脚本 描述目标状态，可以反复执行，第二次执行不会破坏第一次的结果 描述一串动作，通常只能在干净机器上跑一次，重跑会报错或产生重复配置
部署流水线 Deployment pipeline 管的是「应用要跑在什么样的环境上」，产出是环境本身 管的是「代码怎么变成能上生产的制品并送出去」，产出是可发布制品与部署动作。
部署流水线见本章 6.2
容器与云服务 是一种做法：不管底下是虚拟机、容器还是云资源，都用代码声明 是一类技术载体。用了容器和云，照样可以手工点出一堆雪花环境。
容器、微服务与云见本章 6.4
具体工具

最容易混的一点：「我们的环境是用脚本装的」不等于「我们做了 IaC」。 判据不是有没有自动化工具，而是三条 —— 环境的权威定义在不在版本控制里、它描述的是状态还是步骤、实际环境会不会被拉回这份定义。 三条缺一，得到的只是「更快的手工」，漂移照旧。

本对照表为本站教学整理，DOFD 官方文件未以此形式给出该组区分。

④ 工程中怎么用

把一个已经在跑的环境挪进 IaC，不是一次性重写，而是几个可以分别落地的动作：

  • 先接管新环境，再接管老环境：从今天起，新建的环境一律由代码生成。 存量的三台雪花先不动 —— 先让「正确路径」存在，再逐台收编，否则容易变成一个永远做不完的迁移项目。
  • 同一份代码，不同参数出多套环境：开发、测试、预发、生产用同一份定义， 只在规格与容量参数上不同。这一条与本章 6.2 部署流水线 的 「制品只构建一次」是同一个道理：让上生产之前的每一次执行，都是对生产路径本身的演练。
  • 把变更预览当成评审材料：应用之前先生成一份「将要发生什么改动」的差异清单， 评审的人看的是这份清单，而不是工单里的一句自然语言描述。
  • 定期做销毁重建演练：环境能不能从零重建出来，是 IaC 唯一诚实的验收标准。 没演练过的重建能力，等于没有。
  • 把手工改动当缺陷处理：发现实际环境与代码不一致，要问的不是「谁改的」，而是 「为什么改这个东西必须绕过代码」 —— 那通常意味着代码里少了一个可配置项。

以上五条落地动作为本站教学整理，官方文件未规定 IaC 的实施步骤或验收清单。

⑤ 考试怎么考
  • 最主要的命题角度：归属。IaC 被问到时，几乎都是问它属于 CALMS 的哪一个字母、 或属于哪个知识域。答案方向是 A: Automation（自动化）与 M6 Automation & Architecting DevOps Toolchains。 这不是推断：Blueprint 的 A 格描述句逐字把 infrastructure-as-code 与 CI/CD toolchains 并列写在一起 （“CI/CD toolchains, and infrastructure-as-code enable automation, consistency, velocity and fast recovery.”）， 归属题按这句对答案即可。 该句出自 PeopleCert DevOps Foundation Blueprint，官方原文。
  • 第二种角度：定义辨认。给一段描述问是什么实践。 题干里的钥匙词是「用代码 / 用版本控制的文件来定义环境」。 只要出现「环境的定义被提交进代码仓库」这类表述，方向就是 IaC。
  • 干扰项长什么样： 持续集成 / 持续部署（它们管应用代码的流转，不管环境的定义）、 容器化（这是技术载体，不是「把定义写成代码」这件事）、 具体工具名（问的是实践名时，工具名一律不是答案）。 还有一类是把 IaC 说成「一种自动化部署脚本」 —— 少了「版本控制中的声明式定义」这半句，就不成立。
  • 排除技巧：先分清题干在说应用还是环境。 说的是代码怎么合并、构建、测试、上生产 → 是 CI/CD 家族； 说的是机器、网络、资源怎么被创建成某个样子 → 是 IaC。这一刀能切掉大部分干扰项。

IaC 无官方样题答案键条目，以上命题角度、干扰项构造与排除技巧均为本站教学推断； 官方仅公布考试范围为 Bloom 1–2，本站不复制任何官方样题的题干与选项原文。

⑥ 记忆要点

环境不是搭出来的，是从代码里长出来的。

反向自查一句：如果这台机器现在被删掉，能不能在没有任何人回忆的情况下把它重建出来？ 答不上来，就还没有 IaC。

kp-6-3-2

声明式 vs 命令式，与幂等性Declarative vs Imperative · Idempotence

📝 教学整理 ⚠️ 易混淆
① 是什么

声明式 Declarative 描述「我要的是什么状态」； 命令式 Imperative 描述「按什么顺序做哪些动作」。

由此得到 IaC 的关键属性 —— 幂等性 Idempotence： 同一份定义执行十次，结果与执行一次完全相同。 第一次执行会把环境改成目标状态，之后每一次执行都会发现「已经是了」，于是什么都不做。

声明式引擎的三步为什么这三步保证了幂等
读取实际状态先看环境现在是什么样，而不是假设它是干净的
与声明比对算出差异集合。差异为空，说明无事可做
只补差异（收敛）执行的动作由差异决定，不由脚本行数决定。所以执行次数不影响结果

本知识点为本站教学补充， 目的是解释 IaC「声明式」这一要件为什么成立，不作为考纲名词记忆。

② 为什么存在 · 解决什么问题

痛点出现在自动化已经做了一半之后：脚本写出来了，但没人敢跑第二遍。

  • 某团队为初始化环境写了一份 240 行的 shell 脚本，第一次在全新机器上跑得很漂亮。 问题从第二次开始：安装命令遇到已安装的包直接非零退出， 追加配置的那几行把同一段配置又写了一遍，服务起不来。 于是脚本顶部逐渐长出一句注释：「仅限全新机器，勿重复执行」。
  • 更麻烦的是半途失败。某次跑到第 137 行网络抖动中断，前 136 行已经生效。 修好网络之后没人敢重跑整份脚本，只能有人打开脚本肉眼数到第 137 行， 把剩下的命令一条条手工执行。这一刻自动化就已经失效了 —— 最关键的恢复动作重新回到了手工。
  • 团队的补救办法通常是在每条命令前加 if 判断：先检查装没装、改没改、起没起。 加到后来会发现一件事：脚本正在缓慢地重写成一个声明式引擎， 只是这个引擎又慢又不完整，而且没人维护得动。

声明式的价值就在这里：它把「现在是什么状态」的判断责任，从写脚本的人转移给了引擎。 人只需要写清楚想要什么，不需要穷举环境可能处在的所有中间状态 —— 而中间状态的数量，恰恰是手工脚本永远写不完的原因。

本案例与其中的行数为本站构造的教学示例，非真实调研数据。

③ 与相邻概念的区别
维度声明式命令式
代码里写的是 目标状态：「要有一个监听 8080 的 nginx」 动作序列：「装包 → 改配置 → 重启 → 设开机自启」
谁负责判断当前状态 引擎。人只写终点 写代码的人。得预先想清楚环境可能处在的每一种情况
重复执行 无差异则不动作，结果稳定 —— 幂等 可能报错、可能产生重复配置，结果取决于起始状态
部分失败后重试 重新应用一次，引擎自己补齐缺口 需要人定位断点，从中间接着跑
什么时候反而更合适 长期存在、需要反复维持一致的环境 一次性的迁移、切换、数据订正等有明确先后顺序的过程，本来就不该幂等

最容易混的一点：「用 YAML / JSON 写的就是声明式」是错的。 文件格式与执行模型无关 —— 一份把 shell 命令按顺序排成列表的 YAML， 仍然是彻头彻尾的命令式。判断只看一件事： 执行时有没有「先读取实际状态、再计算差异」这一步。有，才是声明式；没有，换什么格式都还是在按顺序做动作。

本对照表与「格式 ≠ 执行模型」这一判据均为本站教学整理，官方文件未以此形式给出该区分。

④ 工程中怎么用
  • 幂等性的验收方法只有一个动作：连着执行两次， 第二次必须报告「0 处改动」。第二次还在改东西，说明这份定义里混进了命令式的成分， 或者有一段配置在被反复覆写。这是一个几分钟就能做完、却极少有人做的检查。
  • 用「预览差异」代替「读代码猜后果」：应用之前先输出「将新增什么、修改什么、销毁什么」。 评审时最该盯的是销毁清单 —— 大多数 IaC 事故都是某个改动意外让引擎决定「先删了再建」。
  • 把顺序性的事情留给命令式，不要硬掰：数据库结构迁移、一次性的数据订正、 新旧系统切换，这些天然有先后顺序、执行一次就该结束的过程， 强行写成声明式只会得到一个别扭的东西。两种范式并存是正常状态，不是妥协。
  • 把偏差检测变成定期任务：定期执行一次「只看不改」的比对， 把实际环境与代码之间的差异报出来。这份报告就是配置漂移的仪表盘， 它的读数长期为零，才说明前一个知识点讲的那道口子真的被堵住了。

以上四条工程动作为本站教学整理，官方文件未规定 IaC 的实施方法或验收标准。

⑤ 考试怎么考
  • 先说清楚边界：declarative、imperative、idempotence 这三个词不在 DOFD v3.4 官方考纲术语表 67 条内， 基础级考试不会要求单独定义它们。学它们是为了理解 IaC 与自动化，不是为了背名词。
  • 它真正的出题形态：藏在对自动化的理解题里。 题干若强调「自动化过程应当可重复、可反复执行、结果一致」， 指向的就是这里的幂等性，答案方向通常落在 Automation 或 IaC 上， 而不是某个具体工具或某条流水线阶段。
  • 干扰项长什么样：最典型的一种是把「自动化」等同于「写了脚本」 —— 选项描述一个「把手工步骤录成脚本」的做法，读起来完全像自动化， 但它缺少可重复执行这一层。另一类是把「快」当成自动化的目的： 自动化的第一价值是一致与可重复，快是它的结果。
  • 排除技巧：遇到描述自动化做法的选项，问一句 「这个做法执行第二次会发生什么」。 答案是「和第一次一样」的那个选项，方向基本正确； 答案是「会出错 / 得看情况」的，通常就是被设计出来的干扰项。

官方未公布命题规律与题型分布，以上出题形态、干扰项构造与排除技巧均为本站教学推断； 官方仅公布考试范围为 Bloom 1–2。本站不复制任何官方样题的题干与选项原文。

⑥ 记忆要点

声明式说要什么，命令式说怎么做；跑十次和跑一次一样，才叫幂等。

一句话自检：敢不敢现在就把这份定义再执行一遍？ 敢，是声明式；心里先咯噔一下，那就还是命令式。

kp-6-3-3

基础设施获得代码的能力，与不可变基础设施Version Control · Review · Test · Rollback · Immutable Infrastructure

📝 教学整理 ⚠️ 易混淆
① 是什么

IaC 真正的收益不在「省了几次点击」，而在于： 基础设施一旦是代码，它就自动继承了整套已经为代码建好的工程能力。 这套能力早就存在，只是过去从来轮不到服务器享用。

继承来的能力应用代码上早就有基础设施因此获得
版本历史 每一行改动都有作者、时间、提交说明 「这台机器为什么是现在这个样子」有一条可追溯的记录链，而不是靠人回忆
代码评审 合入主干前由另一个人看过 环境变更进入同一套同行评审流程，评审对象是具体差异，不是工单里的一句话
自动化测试 静态检查、单元测试、策略校验 环境定义可以被检查：命名规范、必需标签、禁止公网暴露、加密是否开启
回滚 回退到上一个版本重新构建 回退到上一个版本的定义重新应用，环境回到那个已知可用的状态

顺着这条路再走一步，就得到 不可变基础设施 Immutable Infrastructure 🧭 延伸 · 非考纲： 需要变更时不在原地修改，而是用新版本的定义造一台新的、把流量切过去、销毁旧的。 服务器从「需要长期照料的宠物」变成「用完即弃的一次性单元」。

本知识点为本站教学补充， Immutable Infrastructure 只点到概念，不作为考纲名词记忆。

② 为什么存在 · 解决什么问题

痛点是基础设施长期活在工程纪律之外： 同一家公司里，改一行应用代码要过评审、跑测试、留记录； 而改一台生产服务器的内核参数，可能只需要一次 SSH。

  • 某电商在大促前夜，为了扛住流量，有人在生产机上手工调整了一组内核网络参数，当晚确实扛住了。 三个月后同一批机器扩容，新机器没有这组参数 —— 因为它从来没被写下来过。 新机器在流量高峰时表现异常，排查从应用层查起， 花了两天才有人想起「那天晚上好像改过什么」。
  • 更常见的是回滚失败：一次配置变更导致故障，决定回滚。 可「回滚」在这里意味着有人凭记忆把参数改回去 —— 而记忆里通常只有「改了什么」，没有「原来是什么」。 回滚变成了另一次未经评审的变更。
  • 再往下是就地修改的累积效应：一台跑了三年、被无数次就地升级、打补丁、 临时改配置的服务器，没有人能说清它现在的完整状态， 于是没有人敢重装它 —— 它变成了一台不能死也不能重建的机器。

四项能力回答前两条，不可变基础设施回答第三条： 只要每次变更都是「造新的、换掉旧的」，就地修改的历史就永远无法累积， 机器的年龄被强制维持在很短的区间内，它是怎么来的永远只有一个答案 —— 那份定义。

本案例为本站构造的教学示例，用于说明就地修改的累积代价，非真实事件。

③ 与相邻概念的区别
维度可变基础设施（就地修改）不可变基础设施（重建替换）
变更方式 登上这台机器，把它改成新样子 按新定义造一台新的，切流量，销毁旧的
漂移 随时间累积，且不可见 没有累积的时间 —— 机器活不到能漂移的岁数
回滚 反向操作一遍，靠记忆与文档 把上一版的实例重新拉起来 / 把流量切回去
故障排查 先要搞清楚「这台机器现在到底是什么状态」 状态等于定义，排查直接从定义开始
代价 改动快、见效快 需要快速创建实例的能力、流量切换机制，以及状态与数据必须外置

最容易混的一点：「不可变」不是「不能变」，而是「不在原地变」。 不可变基础设施的变更频率往往比传统方式更高 —— 它每天可能重建几十次实例。 被禁止的只有一件事：登录到一台正在运行的机器上去修改它。

本对照表与「不可变 ≠ 不能变」这一判据均为本站教学整理。

④ 工程中怎么用
  • 基础设施仓库走同一套评审流程：不要为环境变更单开一条「更快的通道」。 评审的对象是变更预览的差异清单，评审人重点看新增的对外暴露、被销毁的资源、权限范围的扩大。
  • 给环境定义加自动化检查：把「不允许安全组对全网开放」「必须打成本归属标签」 「存储必须启用加密」这类规则写成可执行的校验，在合入前跑。 这就是把合规从事后审计前移到变更时刻 —— 与第 3 章 DevSecOps（3.5）、 左移（3.1）是同一条思路在基础设施上的应用。
  • 回滚路径要演练：与第 3 章 持续交付（3.3） 里的道理一致 —— 没演练过的回滚等于没有回滚。IaC 的回滚要验证的是 「按旧版定义重新应用之后，环境真的回到了旧状态」，而不只是「代码回退了」。
  • 状态必须外置，不可变才成立：数据库、对象存储、日志要放在实例之外。 一台可以随时被销毁的机器上，不能存放任何销毁后就找不回来的东西。
  • 先从最容易重建的一层开始：无状态的 web 层最适合先做不可变， 有状态的数据层往往长期保持可变。不必全站统一，分层推进即可。

以上工程动作为本站教学整理，官方文件未规定 IaC 或不可变基础设施的实施方式。

⑤ 考试怎么考
  • 最值得注意的一条官方数字：v3.4 官方课程描述把 DevOps 的业务价值量化为 整体 IT 成本下降 15–25%、变更失败率下降 50–70%、供应与部署时间下降最多 90% （DOFD v3.4 Course Description）。 其中「供应（provision）时间」这一项，正是 IaC 直接作用的地方 —— 环境从「提工单等几天」变成「执行一次定义」。引用这三个数字时必须带 v3.4 版本标注， 它们是 v3.4 课程描述给出的区间，v3.6 未重新发布。
  • 命题角度：把收益落到具体机制上。题干若描述「环境的变更有完整记录、可评审、可回退」， 指向的是 IaC 带来的这四项能力，而不是某个流水线阶段或某种测试。
  • 干扰项长什么样： 一类是泛化收益（「减少人力成本」「提高团队士气」）—— 读起来正确，但没有对应到任何具体机制； 一类是张冠李戴，把 IaC 的收益说成持续集成或持续测试的收益； 还有一类是把不可变基础设施说成「基础设施不再变更」 —— 这是对该词的标准误读。
  • 排除技巧：看选项描述的收益能不能追到一个具体动作上。 「可以回退到上一个版本的定义重新应用」能追到动作； 「提升了运维效率」追不到 —— 追不到动作的选项，在基础级考试里通常是干扰项。

三个量化数字出自 DOFD v3.4 Course Description，可引为官方； 「provision 时间对应 IaC」这一关联为本站教学推断。 官方未公布命题规律与题型分布，以上命题角度、干扰项构造与排除技巧均为本站教学推断， 官方仅公布考试范围为 Bloom 1–2；本站不复制任何官方样题的题干与选项原文。

⑥ 记忆要点

基础设施变成代码，就能被评审、被测试、被回滚 —— 从一台不敢碰的机器，变成一份可以讨论的文件。

不可变基础设施一句话：不修，是换。 记住它的反面更有用 —— 一台没人敢重装的机器，就是漂移已经赢了的标志。

与本章其他小节的分工：环境的定义归本节， 代码到制品的流转归本章 6.2 部署流水线，容器与云归 6.4， 工具之间怎么串起来归 6.5。

⭐ 一分钟回忆清单
  • 一句话定义：用版本控制中的声明式代码定义和创建基础设施，而不是手工点击或跑一次性脚本
  • 要杀的敌人：配置漂移 —— 手工搭的环境彼此不一致，「在我这能跑」，故障无法复现，回滚靠记忆
  • 归属：属 CALMS 的 A: Automation 与 v3.4 课程大纲 M6 模块。 这一归属有官方原文撑着 —— Blueprint 的 A 格描述句逐字写 “CI/CD toolchains, and infrastructure-as-code enable automation, consistency, velocity and fast recovery.”。 但 Infrastructure as Code 不在 67 条术语表内，因此本节判「📘 官方模块子项」，不是「⭐ 考纲核心」，也不是「🧭 延伸 · 非考纲」
  • 声明式 vs 命令式：前者写「要什么状态」，后者写「怎么做」。分界不是文件格式，而是执行前有没有「读实际状态、算差异」这一步（本站教学整理）
  • 幂等性：同一份代码执行十次，结果与执行一次相同。验收动作只有一个 —— 连跑两次，第二次必须 0 处改动（本站教学整理）
  • 四项继承能力：版本历史 · 代码评审 · 自动化测试 · 回滚。基础设施因此进入了与应用代码同一套工程纪律
  • 不可变基础设施：不在原地改，而是重建替换。「不可变」≠「不能变」，被禁的只是登机器就地修改（延伸 · 非考纲）
