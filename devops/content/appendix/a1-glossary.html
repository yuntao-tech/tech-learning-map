官方术语表只列词条，不附定义。 因此下表第三列的每一条释义、以及第二列的中文译名，全部是本站措辞， 用于帮助记忆，不是官方原文。唯一的例外是 DevOps 一条 —— 它取自 PeopleCert DevOps Foundation Blueprint 正文定义句的本站译文。

英文原词 中文译名 一句话定义（本站措辞） 主讲小节
Agile Manifesto 敏捷宣言 2001 年发布的四条价值观与十二条原则，把重心从流程与文档转向个体互动、可工作的软件、客户协作与响应变化。 4.2 Agile 与 Scrum
Agile service management 敏捷服务管理 把敏捷的迭代节奏与协作方式带进 IT 服务管理流程，让变更、事件等流程跟得上频繁交付。 4.4 ITSM 与 ITIL
Agile software development 敏捷软件开发 以短迭代、持续反馈、可工作软件为核心的一类开发方法总称，Scrum 是其中最常见的一种。 4.2 Agile 与 Scrum
Application Programming Interface (API) 应用程序编程接口 API 系统之间约定好的调用契约；工具链正是靠它把彼此独立的工具串成一条自动化链路。 6.5 DevOps 工具链架构
CALMS CALMS DevOps 的五个维度 —— Culture、Automation、Lean、Measurement、Sharing，用来判断一个组织在哪一格有短板。 1.1 定义 DevOps
Change failure rate 变更失败率 投入生产的变更中导致服务降级或需要补救的比例，DORA 四指标的稳定性侧之一。 7.2 DORA 四大指标
Change fatigue 变革疲劳 变革推得太多太快又看不到结果，导致人对新一轮变革不再有反应的状态。 5.2 文化债
Change lead time 变更前置时间 从代码提交到该变更在生产环境运行所经过的时间（DORA 口径；价值流口径从需求被接受算起）。 7.4 前置时间 vs 周期时间
ChatOps ChatOps 把运维操作与工具输出放进团队聊天频道执行，使操作过程与上下文对所有人可见。 3.6 ChatOps
Code commit 代码提交 开发者把一段改动提交进版本库的动作，是持续集成的触发点，也是 DORA 口径变更前置时间的计时起点（精益价值流口径自需求被接受起算，见 7.4）。 3.2 持续集成
Collaboration and communication 协作与沟通 DevOps 文化最直接的可观察面：信息是否跨职能流动、坏消息能不能被说出来。 5.1 什么是组织文化
Collective Body of Knowledge (CBOK) 集体知识体 CBOK 组织把分散在个人手里的经验沉淀成可复用、可传播的共享知识资产。 8.1 企业中的 DevOps
Constraint 约束 决定整条价值流最大产出的那一个环节；改善它以外的环节不会提升全局产出。 2.3 约束理论
Containers 容器 把应用与其运行依赖打包在一起的轻量封装，使同一份制品在各环境行为一致。 6.4 云、容器与微服务
Continuous delivery 持续交付 每个通过流水线的版本都随时具备可发布状态，发不发布由人决定。 3.3 持续交付 vs 持续部署
Continuous deployment 持续部署 通过全部自动化测试的版本自动进入生产，没有人工放行环节。 3.3 持续交付 vs 持续部署
Continuous integration 持续集成 开发者频繁把代码合入主干，每次合入都自动构建并测试，尽早暴露集成冲突。 3.2 持续集成
Continuous testing 持续测试 测试贯穿流水线全程而不是堆在末尾，让质量反馈随每次变更即时返回。 3.1 持续测试
Cultural debt 文化债 长期回避的行为与协作问题积累出的欠账，会像技术债一样持续加收利息。 5.2 文化债
Cycle time 周期时间 一件工作从真正开始处理到完成所经过的时间，不含开始之前的排队等待。 7.4 前置时间 vs 周期时间
Deployment frequency 部署频率 单位时间内把变更成功投入生产的次数，DORA 四指标的速度侧之一。 7.2 DORA 四大指标
Deployment pipeline 部署流水线 把构建、测试、部署串成的自动化通道，一次提交沿着它一路走到生产。 6.2 部署流水线
DevOps DevOps IT 组织中的各方协同工作，使计划中的工作快速流动、获得反馈并持续改进直至进入生产，同时达成质量、稳定性、可靠性、可用性、安全与团队满意度。 1.1 定义 DevOps
DevOps metrics DevOps 指标 覆盖速度、质量、稳定性、文化四类的度量集合，目的是驱动改进而不是考核个人。 7.3 速度 / 质量 / 稳定性 / 文化
DevOps roles DevOps 角色 承担具体职责的岗位切面（如 SRE、自动化工程师），与「团队」「干系人」是三个不同的切面。 8.2 角色与团队
DevOps stakeholders DevOps 干系人 对 DevOps 结果有利害关系或有影响力的各方，范围远超开发与运维两个部门。 8.2 角色与团队
DevOps teams DevOps 团队 围绕业务目标组建、覆盖端到端交付所需技能的跨职能团队。 8.2 角色与团队
DevOps toolchain DevOps 工具链 覆盖从计划到运行各环节、通过集成串起来的一组工具；重点在衔接，不在单个工具选型。 6.5 DevOps 工具链架构
DevSecOps DevSecOps 把安全内建进交付流水线并左移到早期，取代发布前的一次性集中安全评审。 3.5 DevSecOps
Dojo Dojo（沉浸式实战训练场） 团队带着真实工作离开日常岗位、在教练指导下集中练习新工作方式的场所。 2.5 第三步：持续改进（实验与学习）
employee Net Promoter Score (eNPS) 员工净推荐值 eNPS 用「是否愿意把本组织推荐给他人」来度量员工投入度的文化类指标。 7.3 速度 / 质量 / 稳定性 / 文化
Epics Epics（大颗粒需求） 大到装不进一个迭代、必须先拆分才能交付的需求条目 —— 是「太大」，不是「最紧急」。 4.2 Agile 与 Scrum
Flow 流动 工作从需求一路向右走到生产、不回头也不积压的顺畅程度，三步工作法第一步的目标。 2.2 第一步：流动
Golden Circle Golden Circle 黄金圈 why / how / what 三层模型，主张先说清目的与信念，再谈做法与产出。 1.2 DevOps 为什么重要
High-performing organizations 高绩效组织 在速度与稳定性两侧同时领先的组织 —— 它的存在说明两者不是取舍关系。 1.2 DevOps 为什么重要
Immersion 沉浸式学习 通过长时间投入真实场景来习得新工作方式的学习方式；Dojo 是场所，Immersion 是方式。 8.1 企业中的 DevOps
Improvement kata 改进型 Kata 设定目标状态、看清当前状态、以小步实验逼近目标的固定改进套路。 2.5 第三步：持续改进（实验与学习）
IT service management IT 服务管理 以服务为单位规划、交付、运营与改进 IT 的管理体系，ITIL 是其中最广泛使用的框架。 4.4 ITSM 与 ITIL
Kanban 看板方法 通过可视化工作流与限制在制品来暴露瓶颈、以拉动方式推进工作的方法。 3.7 看板方法
Kubler-Ross Change Curve Kubler-Ross 变革曲线 描述人面对重大变化时依次经历的情绪阶段，用来预判变革中必然出现的抵触期。 5.3 行为模型
Lean production 精益生产 源自丰田生产方式的制造管理体系，核心是消除浪费、拉动生产与持续改进。 4.3 Lean 与八项浪费
Lean thinking 精益思想 把精益从车间提炼成通用思维：定义价值、识别价值流、让价值流动、由需求拉动、追求尽善尽美。 4.3 Lean 与八项浪费
Lean tools 精益工具 价值流映射、看板、5 Why 等把精益思想落到具体动作上的工具集合。 4.3 Lean 与八项浪费
Lean types of Waste (DOWNTIME) 精益浪费类型 DOWNTIME 精益浪费的八项清单，DOWNTIME 是这八项的首字母助记 —— 比经典七种多出「未被利用的人才」一项。 4.3 Lean 与八项浪费
Mean Time to Repair/Recover (MTTR) 平均恢复时间 MTTR 从服务受损到恢复正常所需时间的平均值，DORA 四指标的稳定性侧之一。 7.2 DORA 四大指标
Microservices 微服务 把系统拆成可独立部署的小服务，让团队不必等待彼此就能各自发布。 6.4 云、容器与微服务
Open source 开源 源码公开、允许自由使用与修改的软件模式；DevOps 工具链大量构建在其上。 6.5 DevOps 工具链架构
Organizational considerations 组织考量 推行 DevOps 之前必须评估的组织侧因素：现状、结构、既有流程与承受变化的能力。 8.4 组织考量与如何起步
Organizational culture 组织文化 组织中被默认接受、真正支配行为的共同假设与规范 —— 看行为，不看墙上的标语。 5.1 什么是组织文化
Resilience engineering 韧性工程 承认故障必然发生，把工程重点放在吸收冲击与快速恢复上，而不是追求不出故障。 3.4 SRE 与韧性工程
Scaled Agile Framework (SAFe) 规模化敏捷框架 SAFe 把敏捷实践扩展到多团队、项目群与投资组合层级的框架。 4.2 Agile 与 Scrum
Scrum Scrum 以固定长度 Sprint 组织交付的敏捷框架，有明确规定的角色、事件与工件。 4.2 Agile 与 Scrum
Scrum roles, artifacts and events Scrum 的角色、工件与事件 Scrum 的三类构成 —— 角色（PO / SM / 开发团队）、工件（产品待办列表等）、事件（Sprint 及其四场会议）。 4.2 Agile 与 Scrum
Service 服务 以结果交付给客户的能力单元：客户享用结果，底层成本与风险由服务提供方承担；ITSM 的管理基本单位就是它。 4.4 ITSM 与 ITIL
Shift left 左移 把测试与安全等活动提前到开发早期并持续进行，把质量内建进开发过程。 3.1 持续测试
Simian Army/Chaos Monkey Simian Army / Chaos Monkey Netflix 用于在生产环境主动注入故障、检验系统韧性的一组工具。 2.6 混沌工程
Single Point of Failure (SPOF) 单点故障 SPOF 一处失效就会拖垮整体的环节；既可能是某个组件，也可能是「只有某个人会做」。 3.4 SRE 与韧性工程
Site Reliability Engineering 站点可靠性工程 SRE 用软件工程的方法解决运维问题、以可靠性为工程目标的实践体系。 3.4 SRE 与韧性工程
Test driven development 测试驱动开发 TDD 先写一条会失败的测试、再写让它通过的实现代码的开发方式。 3.1 持续测试
Testing (unit, acceptance, integration) 测试（单元 / 集成 / 验收） 三个层级的自动化测试：单元验证最小单位、集成验证组件间协作、验收验证是否满足需求。 3.1 持续测试
The Three Ways 三步工作法 流动、反馈、持续改进（实验与学习）三步构成的因果链，是 DevOps 的主轴。 2.1 三步工作法总览
Theory of Constraints 约束理论 系统整体产出由唯一的约束决定，改进必须先找到它并聚焦于它。 2.3 约束理论
Thomas-Kilmann Conflict Modes Thomas-Kilmann 冲突处理模式 按「关注自身诉求」与「关注他人诉求」两轴划分出的五种冲突处理方式。 5.3 行为模型
Value stream mapping 价值流映射 画出一件工作从需求到交付的全部步骤与等待时间，让浪费与瓶颈显形。 4.6 价值流映射
Velocity Velocity 速率 一个 Sprint 内团队完成的故事点数，用于本团队的容量预测 —— 不能跨团队比较，也不是绩效。 4.2 Agile 与 Scrum
Waste 浪费 消耗资源却不为客户创造价值的一切活动。 4.3 Lean 与八项浪费
Waterfall 瀑布 需求、设计、开发、测试、发布依次串行的交付方式，是上述各框架共同的对照系。 4.1 框架全景与彼此关系
