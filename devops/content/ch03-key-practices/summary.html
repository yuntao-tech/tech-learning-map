小节核心结论记忆锚点最易错点
3.1 持续测试
Continuous Testing		 每一次变更在流水线的每个阶段都被恰当的测试判过一遍；左移 = 早 + 持续 + 把质量内建进开发过程 测试是流水线每一格踩着的地板，不是末端的那道闸门 把「有很多自动化用例」当成持续测试；把左移只理解成「测试提前」，漏掉「持续」和「内建质量」
3.2 持续集成
Continuous Integration		 主线每天被合入多次，且每一次合入都被自动化测试判过；必要前提是自动化的单元、集成与验收测试 天天合主线 + 次次自动判，两个条件缺一个就不叫 CI 把「装了一台 CI 服务器」当成在做 CI；把 CI 的前提说成「已经有部署流水线」
3.3 持续交付 vs 持续部署
Continuous Delivery / Deployment		 持续交付 = 随时可以发布，发不发由人决定；持续部署 = 通过全部测试就自动上生产 最后上生产那一下是谁按的：人按是交付，机器按是部署 两者互换；用「有没有部署流水线」当区分依据 —— 两者都有流水线，区别只在人工审批那一步
3.4 SRE 与韧性工程
Site Reliability Engineering / Resilience Engineering		 SRE 用软件工程的方法承担可靠性责任；韧性工程关注系统与组织在意外发生之后还能不能继续工作 SRE 管「怎么把可靠性做出来」，韧性工程问「意外来了还撑不撑得住」 把 SRE 当成运维改了个名；译名写成「弹性工程」（本站统一译「韧性工程」）
3.5 DevSecOps
DevSecOps		 把安全测试并入左移的测试链路，消除把安全评审集中放在 Sprint 之后所造成的延迟 安全不是发布前的一道关卡，是跟测试一起左移的日常动作 题干一提「安全」就选泛泛的 shift left；把 DevSecOps 当成某一类安全扫描工具
3.6 ChatOps
ChatOps		 把交付与运维操作本身放进团队聊天环境执行，让指令、上下文与结果对所有人同时可见 在聊天室里干活，干活的过程自己就变成了共享的日志 把「团队用即时通讯软件沟通」当成 ChatOps —— 关键是操作在对话里被执行，不只是被讨论
3.7 看板方法
Kanban		 可视化工作、限制在制品、管理并度量流动；不规定迭代长度，也不规定角色 看见它、限制它、度量它 把「墙上贴了卡片」当成 Kanban（少了限制在制品就不是）；把 Scrum 的 Sprint 与角色套到看板上
3.8 监控与可观测性 · v3.6 新增
Monitoring and Observability		 监控回答「预先定义的指标是否越界」，可观测性回答「这个没预设过的问题为什么发生」 监控盯已知，可观测性查未知 误以为 Observability 在 67 条官方术语表内 —— 它不在，但它是官方内容：v3.6 学习目标新增项，不是延伸补充
3.9 价值流管理 · v3.6 新增
Value Stream Management / VSM		 对端到端价值流做持续的度量、可视化与优化；价值流映射通常是这个环的第一圈，用来建立基线 映射是拍一张照片，管理是装一台一直开着的监控 与价值流映射混淆：Value stream mapping 在 67 条术语表内，Value Stream Management 不在（但同为官方内容，v3.6 学习目标）
3.10 平台工程 · v3.6 新增
Platform Engineering		 把内部平台当产品运营，为产品团队提供自助能力，交付责任仍留在产品团队手里 平台是产品，开发者是客户，能不能自助是唯一的验收标准 与「DevOps 团队」反模式混淆 —— 平台团队一旦接管了产品团队的运维责任，就退回成新的交接方
表中各节的官方术语名称（Continuous testing / Continuous integration / Continuous delivery / Continuous deployment / Site Reliability Engineering / Resilience engineering / DevSecOps / ChatOps / Kanban 等）均列于 DOFD v3.4 官方考纲术语表； Monitoring and Observability、Value Stream Management、Platform Engineering 出自 PeopleCert 现行产品页公布的学习目标，v3.4 术语表未收录（v3.6 新增），它们同样是官方内容， 三节页头与主题知识点标「📘 官方模块子项」+「🆕 v3.6 新增」。 「记忆锚点」与「最易错点」两列是本站教学整理，官方未以此形式给出复习表。 3.1 / 3.2 / 3.3 / 3.5 四行的核心结论另有 DOFD v3.4 官方样题答案键背书（共 5 条），见下一节； 其余各行的核心结论为本站依据官方模块子项所做的教学归纳。

易混的一对分界线（一句话）诱导你选错的地方
持续交付 vs 持续部署
3.3		 最后一次上生产是不是人工点头：交付要人点头，部署不要 选项两边都写着「自动化的流水线」「通过全部测试」，只在末尾一句话上分叉。官方答案键对这两条各有一次确认，见下一节
持续集成 vs 持续交付
3.2 / 3.3		 CI 保证的是主线随时可构建、可测试；持续交付保证的是产物随时可发布到生产 干扰项把「构建产物可以部署」写进 CI 的定义。CI 的终点在主线的健康，不在生产环境
持续测试 vs 自动化测试
3.1		 自动化测试是手段（把用例变成脚本）；持续测试是编排（每次变更都被恰当的测试判过） 选项写「拥有大量自动化测试用例」「测试全部脚本化」—— 有手段不等于持续，攒一批再一起跑仍然不是持续测试
监控 vs 可观测性
3.8		 监控问「我预先定义的那些指标越界了吗」；可观测性问「这个我从没预设过的现象，为什么会发生」 干扰项把「增加更多仪表盘与告警规则」写成可观测性。仪表盘增多仍然只覆盖已知问题
价值流映射 vs 价值流管理
3.9 / 第 4 章		 映射是一次性画出当前状态、找到约束；管理是对同一条价值流做长期的度量与治理 两者中文只差两个字，英文缩写都能写成 VSM。另一处陷阱：只有 Value stream mapping 在 67 条术语表内（标「⭐ 考纲核心」）；Value Stream Management 不在术语表内，但同样是官方内容 —— v3.6 学习目标，标「📘 官方模块子项」+「🆕 v3.6 新增」
SRE vs 韧性工程
3.4		 SRE 是一套工程实践：用软件工程的方法解决运维问题、承担可靠性；不是一个职位称谓；韧性工程是一个视角：系统与组织在意外下如何继续工作 干扰项把两者当同义词互换。记住 SRE 落在「怎么做」，韧性工程落在「坏了之后会怎样」。两个词都在官方术语表内，不能靠「哪个更官方」来排除
平台团队 vs「DevOps 团队」反模式
3.10 · 「反模式」是本站提法 🧭 延伸 · 非考纲		 平台团队交付自助能力，交付责任留在产品团队；一旦这个团队变成夹在 Dev 与 Ops 之间的第三个交接方，就是反模式 看到「成立一个专门团队」就判错。判据不是有没有新团队，而是有没有新增交接与责任上收
看板 vs Scrum
3.7 / 第 4 章		 看板是持续流 + 限制在制品，不规定迭代长度与角色；Scrum 是固定时长的 Sprint + 规定的角色、工件与事件 干扰项把「用了看板墙」等同于 Kanban 方法，或把限制在制品说成 Scrum 的要素
部署 vs 发布
3.3		 部署是把版本放进生产环境；发布是把功能暴露给用户。特性开关让两者可以分开 （🧭 延伸 · 非考纲 特性开关 Feature toggle 与「发布 Release」均不在 DOFD 考纲术语表内，此处仅用于理解部署与发布的差别） 把「上了生产」直接读成「用户已经能用」。持续部署高频上生产，不等于每次都对用户开放新功能
左移 vs DevSecOps
3.1 / 3.5		 左移是把测试提前且持续这件事本身；DevSecOps 是把安全测试也接进这条左移链路 题干强调「安全评审排在 Sprint 之后造成延迟」时，答案要落到 DevSecOps，而不是泛泛的 shift left。两条都有官方答案键确认
表中官方术语的判定依据是 DOFD v3.4 官方考纲术语表（Concept and Terminology List） 与 PeopleCert 现行 DevOps Foundation 产品页公布的 v3.6 学习目标； 表中另有若干非考纲词（特性开关、反模式等），已就地标注为延伸。 「分界线」与「诱导你选错的地方」两列是本站教学整理，用于描述命题角度与干扰项的构造方式， 官方未以对照表形式给出这些区分，本站也不复制任何官方样题的题干与选项原文。
官方样题答案键确认的本章考点
⭐ 这五条不是推断，是官方确认

本站绝大多数「考试怎么考」都标注为教学推断。下面五条不同 —— 它们来自 DOFD v3.4 官方样题答案键，是关于官方文件的事实陈述： 官方在这些判断上给出了明确的正确答案方向。第 3 章一共占到五条，是全书受官方背书最密集的一章 （这一统计为本站按答案键条目的章节归属整理，官方未按章公布分布）。

  • 持续集成的必要前提是自动化的单元、集成与验收测试。 → 见 3.2 持续集成。 常见误选方向是把『CI 的前置条件』答成与 CI 相关但并非前提的工程条件（例如流水线是否已搭好、代码是否集中管理） —— 判据是：前提必须是能自动判定每次合入是否安全的测试。
  • 依赖部署流水线实现「按需一键部署」的实践是持续交付。 → 见 3.3 持续交付 vs 持续部署。 题面出现「按需」「一键」时落点是持续交付，不是持续部署。
  • 自动部署每个通过单元、集成、用户验收与非功能测试的版本，属于持续部署。 → 见 3.3 持续交付 vs 持续部署。 题面出现「每一个通过测试的版本都自动部署」时落点是持续部署，不是持续交付。 与上一条正好构成一对，必须成对记。
  • Shift left 的含义是通过早期与持续的测试把质量内建到开发过程中。 → 见 3.1 持续测试。 「早期」与「持续」两个成分缺一不可，落点是把质量内建进开发，不是「测试团队提前介入」。
  • 要把安全测试并入左移测试、以消除 Sprint 之后安全评审造成的延迟，需要的实践是 DevSecOps。 → 见 3.5 DevSecOps。 这一条的落点是一个具体实践名，不是「加强左移」这类方向性描述。

本站只陈述这些结论，不复制官方样题的题干与选项原文。 本页其余所有「命题角度」「干扰项长相」的描述，均为本站教学推断，已在各处标注。
