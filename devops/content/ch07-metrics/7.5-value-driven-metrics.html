价值驱动指标Value Driven Metrics

📘 官方模块子项 ⚠️ 易混淆
① 是什么

价值驱动指标 Value Driven Metrics 是以「用户和业务得到了什么」为衡量对象的指标： 它的数值变化对应的是使用、留存、成本、风险、客户结果这类价值流末端的事实， 而不是团队在价值流中间做了多少动作。

三个判定要件说明
有一个受益人能说清「谁因为这个数字变好而变得更好」。答案必须是用户、客户或业务，不能是团队自己
落在价值流末端衡量的是交付之后发生的事：被不被用、有没有替代掉人工、成本降没降，而不是交付过程本身的产出量
变化能改变决定数字变好或变坏时，有人会因此做出不同的选择 —— 继续投入、调整优先级、砍掉功能。做不到这一条的，见 kp-7-5-2

Value Driven Metrics 逐字列于 DOFD v3.4 课程大纲 M7 Measurement, Metrics, and Reporting 的模块子项，属官方模块构成； v3.4 的 67 条官方考纲术语表未单列该词条。上表三个判定要件为本站教学整理，官方未给出判定清单。

② 为什么存在 · 解决什么问题

它要解决的痛点，出现在度量做得「很好」之后： 数据齐、图表多、每周都发，但没有任何一个决定因为这些数字而改变过。

  • 某内部平台团队用一年时间把部署频率从每月 3 次做到每月 40 次， 这条交付流动指标与看板上的四个活动指标一起全部翻倍，季度评审顺利通过。
  • 同一年里，平台的目标用户 —— 公司内 26 个业务团队 —— 只有 3 个把主要流程迁了过来。 其余 23 个继续用旧的工单流程，理由是新平台不支持各自的审批场景。 这条信息不在任何一块看板上，因为没人度量「被采纳」。
  • 机制是这样跑偏的：能量的东西被优先量 → 被量的东西被优先做 → 做得多的方向被当成正确方向。 部署频率容易从流水线自动取数，采纳率要去问 26 个团队， 于是一年之后，团队把力气全花在了容易被量的那一半上。

价值驱动指标切断这条链路的方式，是先定结果，再定动作： 每一块投入先写下「预期哪个末端数字会变化」，再开工。 末端数字没变，无论中间做了多少，都算这块投入没有兑现。

本案例为本站构造的教学示例，数字用于说明机制，非真实调研数据。 「能量→被做→被当成正确方向」这条机制链为本站教学整理。

最容易混的一点：活动指标不等于坏指标。 提交数、故事点在诊断负荷时有用，部署频率、变更前置时间这类交付流动指标在诊断流动问题时非常有用 —— 问题只出在拿任何一类去当价值的证明。 判据不是「这个指标量的是不是活动」，而是「有没有人拿它去回答一个它答不了的问题」。

「活动指标」这一提法与上表四行对照均为本站教学整理， DOFD v3.4 课程大纲 M7 列出 Value Driven Metrics 子项，但未给出与其他指标族的对照表； Value stream mapping、Velocity、Deployment frequency、Change lead time 列于 67 条官方考纲术语表。

④ 工程中怎么用

把一条价值驱动指标真正立起来，需要四个具体动作，缺一条它就会退化成装饰：

  • 每个功能配一条结果假设：立项时写死一句「上线 30 天后，某个末端数字 从 A 变到 B」。 写不出这句话的功能，说明没人知道它为谁解决什么问题。
  • 指标定义写在代码旁边：「使用率」的分子分母各是什么、去不去重、算不算内部账号 —— 定义含糊的指标一定会在争论中被重新解释成好看的那种算法。
  • 反向指标成对出现：只挂「使用量」，团队会去堆弹窗引导； 配上「人工工单量」和「留存」，堆量的做法立刻会在另一个数字上露出代价。
  • 到期就结算：30 天到了必须给结论 —— 兑现、部分兑现、没兑现。 没兑现的功能进入「砍掉 / 改造 / 再等一轮」的明确处置，不允许静静留在系统里。

以上四个动作为本站教学整理，官方文件把 Value Driven Metrics 列为 M7 模块子项， 未规定具体实施步骤或验收周期。

⑤ 考试怎么考
  • 官方已确认的一条：决定哪些 DevOps 原则与实践对组织最有益的，是业务战略与目标 —— 这一判断由 DOFD v3.4 官方样题答案键确认。 它是价值驱动指标在考试里的根：凡是问「指标 / 实践应当对齐什么」，方向永远指向业务目标， 不指向技术先进性、工具能力或团队产出量。
  • 本站教学判据：题干出现「业务价值 / 客户结果 / 对齐业务目标」时， 正确选项通常是描述结果的那一个；出现「产出量 / 完成了多少 / 更快更多」时， 那一般是被排除的干扰方向。
  • 干扰项长什么样： ①用交付流动指标顶替 —— 选项给部署频率或变更前置时间，读起来很像 DevOps 的正确答案， 但它们回答的是交付效率，不是业务价值（这一族属本章 7.2、7.3 的考点）； ②用团队产出顶替 —— 给 Velocity、故事点、提交数； ③用工具或成熟度顶替 —— 给「引入了哪些工具」「达到了哪一级」。
  • 排除技巧：读每个选项时问一句「这句话的主语是团队，还是用户/业务？」 主语是团队的，先划掉一轮，剩下的通常就是价值驱动方向。

以上仅描述命题角度与干扰项构造方式，不复制任何官方样题的题干与选项原文； 除已注明由官方样题答案键确认的一条外，判据与排除技巧均为本站教学推断，官方仅公布考试范围为 Bloom 1–2。

⑥ 记忆要点

价值驱动指标问的是「用户和业务因此得到了什么」，不是「团队做了多少」。

一句话推论：把指标念一遍，如果句子的主语是团队自己，那它多半是活动指标。

kp-7-5-2

活动指标与虚荣指标的识别Activity Metrics & Vanity Metrics

📝 教学整理 ⚠️ 易混淆
① 是什么

活动指标量的是「做了多少」：提交数、故事点、工单关闭数、上线次数。 虚荣指标是另一个维度的判定 —— 指无论怎么变化都不会改变任何决定的数字。

识别方法只有一句话，对任何指标都成立：

这个数字变好了，会因此做出什么不同的决定？

答得出，它是有效指标；答不上来、或者答案是「说明干得不错」，它就是虚荣指标。 注意这条判据不看指标量的是活动还是价值 —— 价值类的数字同样可能是虚荣的。

② 为什么存在 · 解决什么问题

虚荣指标不是被误选的，是被制度筛选出来的： 当指标同时承担「评价人」的功能时，只会上涨的那些数字必然胜出。

  • 某组织把「迭代完成故事点」纳入团队季度评分。两个季度后， 平均 Velocity 从 48 涨到 77，看上去效率提升了 60%。
  • 实际发生的是估点通胀：同样一件事，上季度估 3 点，这季度估 5 点。 没有人作弊，每个人只是在估点时「考虑得更充分了一点」。 交付到用户手上的东西一件没多，而这个数字只会上涨，永远不会下跌。
  • 更深的代价是信息通道被关闭：一旦数字关系到评分， 坏消息就不再往上走。指标从「看清现状的窗口」变成「需要管理的印象」， 这正是第 5 章 文化债（5.2）累积的典型方式之一。

所以虚荣指标的治理不是「换一个更好的指标」，而是切断指标与个人评价的连接。 用指标控制和评价员工不属于 DevOps 领导力的目标 —— 这一判断由 DOFD v3.4 官方样题答案键确认（展开见第 8 章 DevOps 领导力（8.3））。

本案例为本站构造的教学示例，数字用于说明机制，非真实调研数据。 「虚荣指标」一词不在 DOFD v3.4 的 67 条官方考纲术语表内，属本站教学整理的提法。

③ 与相邻概念的区别
维度活动指标虚荣指标价值驱动指标
量什么 做了多少动作 任何东西 —— 活动或价值都可能 用户与业务得到了什么
判定依据 看衡量对象是不是过程动作 看能不能改变决定 看衡量对象是不是末端结果
典型走势 可升可降，反映负荷变化 几乎只升不降（累计值、总量、覆盖数） 会难看，也会停在原地
有没有用 有用：诊断流动与瓶颈的原始材料 没用：占位置，还制造一切正常的错觉 有用：证明投入是否兑现
正确处置 留在团队层，别拿去证明价值 从看板上摘掉 放到产品层与组织层，配上主人

最容易混的一点：活动指标和虚荣指标不是同一个坐标轴上的两个刻度。 前者按衡量对象分类，后者按能否触发决定分类。 一个活动指标（如流水线失败率）完全可以是有效指标， 一个价值类数字（如「累计注册用户总数」）也完全可以是虚荣指标 —— 它只会涨，涨了也不改变任何事。

上表四列对照与「两个坐标轴」这一说法均为本站教学整理，官方未以此形式给出分类； Velocity、DevOps metrics 列于 67 条官方考纲术语表。

④ 工程中怎么用

做一次看板清洗，对每个数字连问四句，任何一句答不上来就摘掉它：

要问的话答不上来说明什么
变好了会做什么不同的决定？核心判据。答案若是「说明干得不错」，这就是虚荣指标
它有可能变难看吗？一个永远不会下跌的数字，不携带任何新信息
谁是这个数字的主人？没有名字的数字，变坏时不会有人动。看板上每个数字都要有主人
能下钻到可行动的层级吗？只有一个总数、点不进去，就无法从「变差了」走到「该改哪里」

清洗的结果通常是指标数量大幅减少。 这是好事：一块屏幕上放 30 个数字，等于一个都没放 —— 没人能同时盯 30 个方向。

这套四问清洗法为本站教学整理，官方文件未给出指标筛选流程。 其中「切断指标与个人评价的连接」这一原则的官方依据是： 用指标控制和评价员工不属于 DevOps 领导力的目标（由 DOFD v3.4 官方样题答案键确认）。
⑤ 考试怎么考
  • 官方已确认的一条：用指标控制和评价员工不属于 DevOps 领导力的目标 —— 由 DOFD v3.4 官方样题答案键确认。 这是本节最可能被直接命中的考点，且常以反向问法出现（问「以下哪一项不是」）。 凡把指标用于考核 / 控制个人的方向，在 DOFD 语境下一律不成立。
  • 干扰项长什么样：与正确答案并列的干扰方向，通常是 DevOps 领导力语境下本身成立的正面表述， 因此不能靠「哪个听起来不好」来选，只能靠「哪一项把指标指向了人而不是系统」来定位。 难点不在识别，而在紧张时把「不是」读成「是」。
  • 排除技巧（本站整理）：遇到指标相关的选项，看它是朝向系统还是朝向人。 朝向系统（看清流动、暴露约束、验证结果）的表述在 DevOps 语境里是对的； 朝向人（排名、考核、问责个人）的表述一律是错的方向。
  • 与本章 7.1 的呼应：度量的三种误用在本章 7.1 为什么必须度量 展开，本节只负责「量错对象」这一类误用。

以上仅描述命题角度与干扰项构造方式，不复制任何官方样题的题干与选项原文； 除已注明由官方样题答案键确认的一条外，判据与排除技巧均为本站教学推断。

⑥ 记忆要点

答不出「会因此做什么不同的决定」，这个数字就是虚荣指标。

补一条走势判据：只会涨、不会跌的数字，几乎一定是虚荣的。 指标的价值来自它有可能变难看。

DevOps 看板的分层设计DevOps Dashboards

🆕 v3.6 新增 📝 教学整理
① 是什么

DevOps 看板 DevOps Dashboards 是把指标持续呈现给特定受众、用于触发决定的视图。 它的设计单位不是「指标」，而是「谁在看 · 看到之后能做什么」。

四条设计原则含义
面向受众分层团队看流动，管理层看结果。同一块屏幕服务不同受众，结果是谁都用不上
显示趋势而非快照单个数值无法判断好坏。「87%」不带上下文毫无意义，「连续四周从 95% 掉到 87%」才是信息
能下钻到可行动层级从「变差了」必须能点到「哪条服务、哪个环节、哪一批变更」，否则看见了也动不了
每个数字都有主人每条指标写上一个具体的人或团队。没有主人的数字，变红了只会被截图，不会被处理

DevOps Dashboards 属 v3.6 新增学习目标 （出自 PeopleCert 现行 DevOps Foundation 产品页公布的学习目标）， v3.4 的 67 条官方考纲术语表与 M7 模块子项均未收录。 上表四条设计原则为本站教学整理，官方未公布看板的设计规范。

② 为什么存在 · 解决什么问题

看板出问题的方式很固定：先做成一块给所有人看的大屏，再变成没人看的大屏。

  • 某公司在办公区挂了一块「统一 DevOps 大屏」，18 个指标一屏排满， 从流水线时长一直到季度营收，全部用红黄绿三色块显示。
  • 团队看不到自己能动的东西 —— 屏幕上是全公司 40 个服务的汇总， 自己那条流水线的时长被平均掉了。管理层也看不出结论 —— 绿色只说明「大多数还行」，而真正出问题的那两个服务被平均值遮住了。
  • 三个月后这块屏幕的作用只剩一个：季度汇报截图。 指标只往上汇总、不往下反馈，团队从来没从这块屏上得到过一条可以行动的信息。

分层设计要解决的正是这件事：不同受众的决策周期和可行动范围根本不同。 团队的动作以天计，管理层的动作以季度计； 把两者塞进同一张表，等于让两边都拿到对自己无效的粒度。

本案例为本站构造的教学示例，用于说明分层的必要性，非真实调研数据。

③ 与相邻概念的区别
对比对象看板 Dashboard它
汇报报表 为做决定而存在，天天看，允许难看 为说明情况而存在，周期性产出，天然倾向于好看。看板一旦只在汇报前被打开，它已经变成报表

见第 3 章 Kanban（3.7）

最容易混的一点：中文的「看板」同时对应 Dashboard 与 Kanban 两个完全不同的英文词。 Kanban 是 67 条官方考纲术语表里的工作流管理实践（属 M3 关键实践）， DevOps Dashboards 是 v3.6 新增的指标呈现主题。 看到中文「看板」，先确认原词是哪一个。

④ 工程中怎么用

建看板时按分层原则落地，同时避开三条最常见的反模式：

反模式它长什么样 · 为什么有害
做成给领导看的成绩单 看板只在季度汇报前被打开，指标选择的标准变成「哪个好看放哪个」。 一旦它承担评价功能，坏消息就不再出现在上面 —— 而看板存在的意义正是尽早暴露坏消息
指标只上不下 数据层层向上汇总给管理层，却从不以团队可用的粒度回流。 团队被要求提供数据，却从数据里得不到任何东西， 下一步必然是应付式填报，源头数据随之失真
用红黄绿掩盖真实分布 「95% 的服务是绿的」听起来很好，但出事的永远是那 5%。 三色块把分布压成一个字，长尾、离群点、正在恶化的趋势全部消失。 正确做法是保留分布与趋势线，颜色只做辅助标记

落地时的具体检查动作：

  • 一层一屏，一屏不超过 7 个数字。放不下说明还没想清楚这一层的人要做什么决定。
  • 每个数字旁边写主人的名字。写不出名字的先摘掉，别留在上面占位。
  • 每个数字都能点开。点不开的数字只能引发追问，不能引发行动。
  • 默认显示区间而不是当前值：至少四个周期的趋势，配上正常波动范围。
  • 定期做减法：每季度砍掉过去三个月里一次也没触发过决定的指标。
三条反模式与上述检查动作均为本站教学整理，官方未公布看板反模式清单。 DevOps Dashboards 作为主题属 v3.6 新增学习目标（出自 PeopleCert 现行 DevOps Foundation 产品页公布的学习目标）； 「不以指标评价个人」这一条的官方依据是 DOFD v3.4 官方样题答案键确认的判断 ——「用指标控制和评价员工不属于 DevOps 领导力的目标」。
⑤ 考试怎么考
  • 版本定位先记牢：DevOps Dashboards 是 v3.6 新增的学习目标， v3.4 的 67 条术语表与 M7 模块子项里都没有它。 而 Value Driven Metrics 在 v3.4 的 M7 子项中已逐字存在。两者的版本身份不同，容易记反。
  • 命题角度：Bloom 1–2 层级下，看板类题目通常问用途而非实现 —— 「看板的目的是什么」「哪一项描述了合理的看板做法」。 正确方向永远是「让相关方看见真实情况以便做出决定」。
  • 干扰项长什么样： ①考核导向 —— 「用于评估团队绩效 / 对团队排名」， 这一方向由 DOFD v3.4 官方样题答案键确认为错误（用指标控制和评价员工不属于 DevOps 领导力的目标）； ②工具导向 —— 「集成尽可能多的工具数据源」，把手段说成目的； ③展示导向 —— 「向管理层展示 DevOps 转型的成果」，听着正面，但落点是汇报不是决策。
  • 排除技巧（本站整理）：看选项的落点是「让人做出更好的决定」 还是「让人被更好地评价」。后者一律排除，无论表述多正面。
  • 时间分配提示：本章 v3.4 最多出 2 题，占 40 题的 5%、八个模块最低 （DOFD v3.4 Examination Requirements，2022-05；v3.6 未公开重新发布权重表）。 看板部分按理解学，不要按应试时间投入 —— 记住「分层 + 有主人 + 能下钻」这一层即可，不必深挖实现。

以上仅描述命题角度与干扰项构造方式，不复制任何官方样题的题干与选项原文； 除已注明由官方样题答案键确认的一条外，命题角度分析与排除技巧均为本站教学推断， 官方仅公布考试范围为 Bloom 1–2，未公布 v3.6 的题数分布。

⑥ 记忆要点

看板上每个数字，都要有一个主人的名字和一个可能的动作。

分层口诀：团队看流动、产品看使用、组织看结果； 三层粒度不同，但必须能下钻到同一批原始数据。

中文陷阱提醒：Dashboard 和 Kanban 在中文里都叫「看板」， 考试里见到 Kanban 一律指工作流管理实践，不是 Dashboard。
