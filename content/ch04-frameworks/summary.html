4.8 本章总结与练习

Chapter Summary
📖 本章总结 ⚠️ 易混淆汇总

本章考的从来不是 Agile、Lean、ITSM 各自的内部流程，而是它们与 DevOps 的关系，以及彼此的分工。 六个框架看似各说各话，放到同一条价值流上就会各就各位： 有的管上游怎么切工作，有的管下游怎么运行服务，有的管整条流怎么被看见，有的管钱怎么进来，还有一个管人敢不敢说真话。 这一页把它们摆回原位，再把两条有官方答案键背书的结论单独拎出来。

小节核心结论记忆锚点最易错点
4.1 框架全景与彼此关系
Related Frameworks		 DevOps 不替代 Agile / Lean / ITSM，而是把它们接到同一条价值流上。Blueprint 的 Related Frameworks 一栏逐字给出四项定位：Agile: Lean Development、ITSM: Processes、Lean: Reduce Waste、Value Stream Management: End-to-End 本章考的是「关系」，不是各框架的内部流程 把本章当成 Agile 或 ITIL 的入门课去背内部流程；答题时选「DevOps 取代了 Agile / ITSM」这类替代式表述
4.2 Agile 与 Scrum
Agile / Scrum		 Agile 是一组价值观与原则（Agile Manifesto）；Scrum 是实现 Agile 的一种具体框架，规定了角色、工件与事件 Agile 说「为什么这么干」，Scrum 说「具体怎么排」 把 Agile 与 Scrum 当同义词；把 Velocity、Epics 当成 Agile 的定义要素（它们是 Scrum 侧的度量与工作项）
4.3 Lean 与八项浪费
Lean / Waste		 Lean 的主轴是识别并消除不产生客户价值的活动。官方术语分三层：Lean thinking（思维）、Lean production（生产体系）、Lean tools（工具） 浪费问「哪些活动白做了」，约束问「哪一环决定整体速度」 把浪费与约束当同义词；把 Lean thinking / Lean production / Lean tools 混成一个词作答
4.4 ITSM 与 ITIL
IT service management		 术语表内的是 IT service management —— 管理 IT 服务的实践总称；ITIL 是它最流行的一套具体框架实现。官方答案键确认：对 DevOps 最关键的 ITSM 流程是组织变革管理、服务连续性管理、事件管理三者皆是 ITSM 是学科，ITIL 是其中一本教材 把 ITSM 与 ITIL 当同义词；在「哪个 ITSM 流程对 DevOps 最关键」上挑单一流程 —— 官方答案是三者皆是
4.5 安全文化与学习型组织
Safety Culture / Learning Organizations		 安全文化 Safety culture指可以安全地说出坏消息的文化。官方答案键确认：面对指责与恐惧文化、大量单点故障、频繁战情室的组织，应转向安全文化 安全文化 = 说真话不受罚，与信息安全无关 把 Safety culture 读成信息安全或 DevSecOps；误以为这两个主题词在 66 条术语表内 —— 都不在
4.6 价值流映射
Value stream mapping		 把一条价值流的每个环节与每段等待时间画出来，据此找出浪费与约束。它是官方术语表条目，也是 Lean 的识别手段 先让浪费被看见，才谈得上消除 与 Value Stream Management 混淆 —— 表内的是 mapping，不是 management；把它答成「持续采集的流动指标」（那是 Value Stream Management）；画出的图上没有任何等待时间数字 —— 那只是流程图，不是价值流映射
4.7 持续资金
Continuous Funding		 把预算从按项目一次性审批改为按产品 / 价值流持续投入，让长期存在的团队不必为每次投入重新立项 给团队持续拨款，不给项目一次性拨款 误以为 Continuous Funding 在 66 条术语表内（不在，它是 M4 官方模块子项）；把它理解成「不断追加预算」
表中官方术语名称（Agile Manifesto、Agile software development、Scrum、Scrum roles, artifacts and events、 Lean thinking、Lean production、Lean tools、Waste、IT service management、Value stream mapping 等） 均列于 DOFD v3.4 官方考纲术语表（Concept and Terminology List）； Agile、ITSM、Lean、Safety Culture、Learning Organizations、Continuous Funding 是 DOFD v3.4 课程大纲 M4 Business and Technology Frameworks 的官方模块子项。 4.1 行引用的四项定位逐字出自 PeopleCert DevOps Foundation Blueprint 的 Related Frameworks 一栏。 「记忆锚点」一列为本站教学整理，官方未以此形式给出复习表； 「最易错点」一列中，4.4 行的「官方答案是三者皆是」出自 DOFD v3.4 官方样题答案键， 4.5 / 4.6 / 4.7 行关于「是否逐字出现在 66 条术语表内」的判断出自 DOFD v3.4 官方考纲术语表与 v3.4 课程大纲 M4 模块子项， 其余措辞（易错倾向、常见误读）为本站教学整理。 「核心结论」一列除标明出自 Blueprint（4.1 行）与官方样题答案键（4.4 / 4.5 行）的部分外， 其余为本站依据官方术语名所作的教学表述 —— 官方只公布术语名称，未公布这些定义句。
官方术语逐字写作 Lean types of Waste (DOWNTIME)，本身不带数量词；DOWNTIME 由八个首字母构成，对应八项浪费 （经典精益七种 TIMWOOD 加上 Non-utilized talent），这一层来龙去脉属本站教学整理。 4.7 行「按项目一次性审批 → 按产品持续投入」这一对比框架，是对 Continuous Funding 通行含义的本站教学整理， 官方大纲只给出子项名称、未附定义句。

这九对是本站判断最容易被相邻选项拖走的地方（本站教学整理，官方未公布干扰项构造方式与易错点分布； 模块级的最多题数分布见本页「本章在考试中的位置」）。 看表的方法：先记「分界线」那一列，再记「诱导你选错的地方」；能一句话说出分界线，这一对就丢不了分。 其中一行是一组三个词（Lean thinking / production / tools），判定方式相同。

易混的一对分界线（一句话）诱导你选错的地方
DevOps vs Agile
4.1 / 4.2		 Agile 主要解决「怎么把需求做出来」（开发侧的迭代与响应变化）；DevOps 把这条流延长到生产环境与运维，让计划中的工作快速流动、获得反馈并持续改进 选项把 DevOps 写成「Agile 的升级版」或「取代 Agile 的新方法」。Blueprint 把 Agile 列在 Related Frameworks 里，是相关框架，不是被替代对象
Agile vs Scrum
4.2		 Agile 是价值观与原则（Agile Manifesto）；Scrum 是一种实现框架，规定了角色、工件与事件 选项用 Scrum 的具体元素（Sprint、Velocity、Scrum 角色）去定义 Agile。能用 Scrum 之外的方式做 Agile，反过来不成立
ITSM vs ITIL
4.4		 ITSM 是学科 / 实践总称（官方术语 IT service management）；ITIL 是这门学科里一套具体的框架实现 选项把两者当同义词互换。判定线索：66 条术语表里只有 IT service management，没有 ITIL，题面通常也用 ITSM 而非 ITIL
安全文化 vs 信息安全
4.5 · 与 3.5 DevSecOps 对照		 Safety culture 关心人敢不敢说出坏消息（心理安全）；信息安全 / Security 关心系统会不会被攻破。两者中文都带「安全」，含义完全不同 题干出现「安全」就往 DevSecOps 上靠。官方答案键确认的场景是指责文化、单点故障、频繁战情室 → 安全文化，落点是文化，不是安全测试
浪费 vs 约束
4.3 · 与 2.3 约束理论 对照		 Waste 是不产生客户价值的活动，哪里都可能有，可以并行消除；Constraint 是决定整条流速度的那一环，同一时刻通常只有一个 选项把「消除浪费」与「提升约束」当成同一件事。判据：浪费问「白做了什么」，约束问「谁在定速度」；消除非约束环节的浪费不会让整体变快
价值流映射 vs 价值流管理
4.6 · 3.9 价值流管理		 映射是一次性画出当前状态、找出浪费与约束；管理是对同一条价值流做长期的度量、可视化与治理 两者中文只差两个字，英文都能缩成 VSM。另一层陷阱：Value stream mapping 在 66 条术语表内，Value Stream Management 不在（后者出现在 Blueprint 的 Related Frameworks 与 v3.6 学习目标中）
项目制资金 vs 产品制资金
4.7 📝 教学整理		 项目制：按一次性立项审批预算，项目结束团队解散；产品制 / 持续资金：按长期存在的产品与价值流持续拨款，团队稳定 选项把持续资金写成「预算不封顶」或「随时追加预算」。分界不在金额多少，而在拨款对象是一次性的项目，还是长期存在的价值流
Lean thinking / production / tools 三层
4.3		 三个都是官方术语、三个不同层次：Lean thinking 是思维方式，Lean production 是一整套生产体系，Lean tools 是具体手段 选项把三者随意互换。不能靠「哪个更官方」排除 —— 三个都在 66 条术语表内，只能靠层次判断
Scrum vs Kanban
4.2 / 3.7 看板方法		 Scrum 是固定时长的 Sprint + 规定的角色、工件与事件；Kanban 是持续流 + 限制在制品，不规定迭代长度与角色 选项把「限制在制品」写成 Scrum 的要素，或把 Velocity 安到看板上。两个词都在术语表内，只能靠「有没有固定迭代与规定角色」区分
表中是否官方术语的判定依据是 DOFD v3.4 官方考纲术语表（Concept and Terminology List）与 v3.4 课程大纲 M4 模块子项； Value Stream Management 的位置依据 PeopleCert DevOps Foundation Blueprint 的 Related Frameworks 一栏与 PeopleCert 现行产品页公布的 v3.6 学习目标。 「安全文化 vs 信息安全」行与「浪费 vs 约束」行的分界线中，安全文化与约束的落点分别有官方答案键与官方术语支持， 但两列的「分界线」「诱导你选错的地方」措辞均为本站教学整理，用于描述命题角度与干扰项的构造方式，官方未以对照表形式给出这些区分。 「项目制 vs 产品制资金」一行按本站教学整理呈现：官方大纲只给出 Continuous Funding 子项名称，未附定义句。 本站不复制任何官方样题的题干与选项原文。
官方样题答案键确认的本章考点
⭐ 这两条不是推断，是官方确认

本页绝大多数「命题角度」都标注为教学推断。下面两条不同 —— 它们来自 DOFD v3.4 官方样题答案键，是关于官方文件的事实陈述：官方在这两个判断上给出了明确的正确答案方向。

  • 对 DevOps 最关键的 ITSM 流程是组织变革管理、服务连续性管理、事件管理 —— 三者皆是。 → 见 4.4 ITSM 与 ITIL。 这一条的价值不只是答案本身，还在于它说明官方把 ITSM 看作与 DevOps 多点耦合的框架，而不是只在事件管理一处相接。 常见误选方向是从三个流程里挑出一个自己最熟的（多数人挑事件管理）。
  • 面对指责与恐惧文化、大量单点故障、频繁战情室的组织，应转向安全文化。 → 见 4.5 安全文化与学习型组织。 落点是文化层面的转向，不是补一轮安全测试、也不是先去消灭单点故障 —— 题面里的单点故障与战情室是症状，不是要治的病。

本站只陈述这两条结论，不复制官方样题的题干与选项原文。 本页其余所有「命题角度」「诱导你选错的地方」的描述，均为本站教学推断，已在各处标注。
