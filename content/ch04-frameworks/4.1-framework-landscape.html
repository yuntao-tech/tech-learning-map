② 为什么存在 · 解决什么问题

这份清单出现之前，IT 组织里已经同时跑着好几套框架，但没有一份东西说明它们之间是什么关系。 具体场景：

  • 某企业的三套节奏各自为政：开发按 Scrum 的两周迭代跑， 运维按 ITIL 的变更窗口跑（每月两个窗口，CAB 会议审批）， 预算按项目制年度拨款（钱在年初一次分完，中途改需求要走立项变更）。
  • 结果是需求全卡在交接处：迭代结束时功能已经可用，却要等下一个变更窗口； 等到窗口，预算口径又对不上。每一套框架在自己的范围内都在正常运转， 端到端的交付却看不出任何改善。
  • 没有一份统一清单时，转型只能逐个框架各自局部优化 —— 敏捷教练把迭代做得更顺，ITSM 顾问把变更流程做得更规范， 两边都交了合格的报告，谁也说不清边界该画在哪、哪一段本来就该由对方负责。

本案例为本站构造的教学示例，用于说明多框架并行时的交接失效机制，非真实调研数据。

清单的作用，就是把这些名字摆到同一张图上，先划出各自覆盖哪一段， 才谈得上接口怎么接。图 4-1-1 就是这张图。

官方文件本身给出了一个方向性判断： 决定哪些 DevOps 原则与实践对组织最有益的，是业务战略与目标 —— 由 DOFD v3.4 官方样题答案键确认。 这句话的含义是：框架不是按「哪个更先进」来选的，而是按它接在这条价值流的哪一段、解决哪个具体问题来选的。 清单的作用，就是把候选项限定在这几个名字上。

v3.6 之所以在框架层补上 VSM 与 SRE，也是同一个逻辑： 这两者已经不再只是「实践」，而是被当作组织层面的方法体系来用了。 （这一解释为本站教学整理，官方仅公布了学习目标清单，未说明加入原因。）

⑤ 考试怎么考

复习方向最容易错在这里：把两周时间花在背 Scrum 的角色工件与几十个 ITSM 流程名上， 却答不出「DevOps 从 Agile 继承了什么」 —— 而框架的内部细节，正好是干扰项的原料。 （此提示为本站教学整理。）

  • 命题角度一：清单归属。给出若干名字，问哪一个属于（或不属于）业务与技术框架。 六项是硬清单，直接对照即可。
  • 命题角度二：方向判断。决定哪些 DevOps 原则与实践对组织最有益的是业务战略与目标 —— 这一条由 DOFD v3.4 官方样题答案键确认。凡是问「按什么来选」的题， 答案方向是业务侧，不是技术侧。
  • 干扰项长什么样： 框架内部细节（某框架的角色数、流程数、仪式名）—— 题干在问 DevOps 与框架的关系，选项却在描述框架自己的内部机制，这类选项通常可以整组划掉； 具体厂商工具名（框架层的题不会用工具名作正确答案）； 看起来更「先进」的技术名词（用来诱导凭印象选新词）。
  • 排除技巧：先看题干问的是「关系」还是「内部」。 M4 的题几乎都在问关系；选项一旦滑进某个框架的内部构造，就与题干不在同一层。
  • 关于版本：版本沿革本身不是考纲列出的知识点， 两份清单要记不是为了答版本题，而是为了不被「这个不在考纲里吧」这种自我怀疑干扰。 （官方未公布题目层面的排除清单，此为本站教学提示。）

以上仅描述命题角度与干扰项构造方式，不复制任何官方样题的题干与选项原文； 干扰项分析与排除技巧为本站教学整理，官方仅公布考试范围为 Bloom 1–2。

① 是什么

这是本章唯一必须记牢的一句话： DevOps 不提供任何一个框架的替代品，它把这些框架接到同一条价值流上。

这个判断有官方依据。PeopleCert DevOps Foundation Blueprint 有一栏叫 Related Frameworks（相关框架），逐字原文是：

Blueprint 逐字原文它说了什么
Agile: Lean Development敏捷这一栏挂着的是精益开发；官方只给出这行对应关系，未说明二者是并列、包含还是同源 —— 本站不替官方定性
ITSM: ProcessesITSM 贡献的是流程，即运营侧的纪律

上表左列为 PeopleCert DevOps Foundation Blueprint 的逐字原文，可直接引用； 右列的中文解读与「叫相关框架而不叫被取代的框架」这一推论，是本站教学整理。 Agile: Lean Development 一条的字面含义存在多种读法 （「敏捷即精益开发」或「敏捷之下的精益开发」），本站只陈述官方原文并给出中性解读，未替官方定性。
② 为什么存在 · 解决什么问题

这句话解决的痛点，是把 DevOps 当成一次「换框架」的组织改造。具体场景：

  • 某企业启动 DevOps 转型，口号是「敏捷已经过时了，我们直接上 DevOps」。 第一步取消了 Scrum 的迭代评审，理由是「持续交付了还要迭代干什么」； 第二步把变更管理流程停掉，理由是「审批就是官僚」。
  • 三个月后的结果：迭代评审没了，需求方失去了固定的反馈入口， 改需求变成随时插队，在制品越堆越多；变更管理没了， 生产上出了故障查不到是谁在什么时候改了什么，事件复盘无法进行，年度审计直接不通过。
  • 补救方式是把两者又装了回去 —— 但这时候它们变成了「DevOps 之外的额外流程」， 团队认为是倒退，抵触更强。拆掉容易，接回去很贵。

本案例为本站构造的教学示例，用于说明「取代式转型」的失败机制，非真实调研数据。

正确的机制是接线，不是拆换：Agile 那一段的迭代与响应变化继续保留， 只是它的终点从「可工作的软件」延长到「在生产上稳定运行」； ITSM 的变更与事件纪律继续保留，只是审批从会议变成自动化闸门与预授权。 每个框架的价值被继承，它挡住流动的那一部分被改造。

这与第 2 章 三步工作法（2.1）是同一件事的两个层面： 三步工作法讲的是流动、反馈、持续改进这条因果链，本节讲的是哪个框架接在这条链的哪一段。

③ 与相邻概念的区别
框架它解决什么问题DevOps 从它继承什么最容易被混淆的那一点
Agile 需求会变，长周期计划必然失准 —— 用短迭代把计划切小 迭代与响应变化：小批量、频繁交付、拥抱变更 以为 DevOps 是 Agile 的下一代。实际上 Agile 通常止于「可工作的软件」， DevOps 接的是它之后直到生产运行的那一段
Lean 工序之间堆积库存与等待，整体交期被拖长 流动与消除浪费：等待、返工、在制品堆积都是要消掉的浪费 以为 Lean 只是「做减法」。它真正给的是把价值流当整体看的视角， 局部效率高不等于整体流动快
ITSM 系统上线之后没人管，变更无记录、事件无响应、服务无承诺 服务与运营纪律：变更、事件、服务连续性的管理方式 以为 DevOps 意味着不要流程。DevOps 反对的是拖慢流动的流程形态， 不是流程本身 —— 官方样题答案键的方向恰恰相反（见 ⑤ 面）
安全文化 坏消息说不出口，问题只能等到爆炸时才被看见 「能说真话」的前提：无指责的复盘、故障可以公开讨论 把 Safety Culture 当成信息安全。它指的是「可以安全地说出坏消息」， 与 DevSecOps 不是一回事
VSM 各环节都说自己很快，端到端交付却很慢，且没人有全局数据 端到端的度量与可见性（Blueprint 原文：End-to-End） 与价值流映射 Value stream mapping混用。 映射是一次性的分析动作，管理是持续的运营方式
SRE 可靠性靠人盯、靠加班，无法量化也无法工程化 把可靠性当成工程问题来设计与度量 与 ITSM 抢地盘。两者覆盖同一段价值流， 差别在用服务流程管，还是用工程手段解

最容易混的那一点，六行里其实是同一个： 把「DevOps 与 X 的关系」读成了「DevOps 还是 X，二选一」。 只要选项里出现「取代 / 替换 / 不再需要」这类词，方向基本就是错的。

④ 工程中怎么用

组织里已经有一堆框架时，逐个过一遍这三问，答案决定它是留、是改、还是撤：

  • 问一：它接在价值流的哪一段？ 答不上来，说明这个框架在组织里已经只剩形式（例如「敏捷」只剩每日站会，不影响任何交付节奏）。
  • 问二：它现在提供的是价值，还是延迟？ 变更评审会如果在做风险判断，是价值；如果只是走个签字流程，那是延迟。 同一个流程在两个组织里可以是相反的答案，必须看实际发生了什么。
  • 问三：如果明天把它撤掉，谁会先出问题？ 没人出问题 → 它早就是形式了；审计、客服、财务先出问题 → 它承担着组织的真实约束， 要做的是把它做快，不是拆掉。

改造的方向永远是保留职责、改变形态： 变更管理保留可追溯的授权记录，但把「开会审批」换成「自动化闸门 + 低风险变更预授权清单」； 迭代评审保留固定的反馈入口，但把评审对象从「演示环境」换成「生产上的真实数据」。

这套「三问 + 保留职责改变形态」的判断方法为本站教学整理， 官方文件列出了框架清单与各自的贡献，未给出框架取舍的判断流程。
⑤ 考试怎么考
  • 官方已确认的一条 · ITSM： 对 DevOps 最关键的 ITSM 流程是「组织变革管理、服务连续性管理、事件管理」三者皆是 —— 由 DOFD v3.4 官方样题答案键确认。 这条特别值得记，因为它同时证明了两件事：官方并不认为 DevOps 排斥 ITSM 流程； 以及在这一类题上，「以上皆是」可以是正确答案，不要因为它看起来太省事就跳过。三个流程的展开见 4.4 ITSM 与 ITIL。
  • 官方已确认的一条 · 安全文化： 面对指责与恐惧的文化、大量单点故障、频繁的战情室这一组现象的组织， 应当转向安全文化 —— 由 DOFD v3.4 官方样题答案键确认。 这是典型的「症状 → 框架」题型：题干给现象，选项给框架名。症状束与排除法见 4.5 安全文化与学习型组织。
  • 干扰项长什么样： 最常见的一类是取代式表述 —— 「DevOps 取代 ITSM」「有了 DevOps 就不需要流程 / 不需要变更管理」。 第二类是张冠李戴：把某个框架的贡献安到另一个头上（例如说消除浪费来自 Agile、迭代来自 Lean）。 第三类是把安全文化理解成信息安全，于是「症状 → 框架」题的答案被换成 DevSecOps。
  • 排除技巧： 第一步，划掉一切含「取代 / 替换 / 不再需要 / 淘汰」的选项； 第二步，回到 Blueprint 的四条对应关系 —— Agile 给迭代、Lean 给消除浪费、ITSM 给流程、VSM 给端到端， 哪一条被挪了位置，那个选项就是错的。 （四条对应关系出自 Blueprint 逐字原文；把它当排除工具用是本站教学整理。）
  • 反向问法：问「以下哪一项不是 DevOps 与相关框架的关系」， 正确答案往往就是那个写着「取代」的选项。

以上仅陈述官方样题答案键确认的结论与命题角度， 不复制任何官方样题的题干与选项原文； 干扰项分类与排除技巧为本站教学整理，官方仅公布考试范围为 Bloom 1–2。

⑥ 记忆要点

DevOps 不换掉任何一个框架，它把它们接到同一条价值流上。

Blueprint 四条对应关系，按贡献记： Agile 给迭代与响应变化 · Lean 给流动与消除浪费 · ITSM 给服务与运营纪律 · VSM 给端到端； 再补一条不在这四条里但同样关键的：安全文化给「能说真话」的前提。

只要选项里出现「取代」两个字，先怀疑它。（此提示为本站教学整理。）

kp-4-1-3

Waterfall：所有这些框架共同的对照系Waterfall

⭐ 考纲核心⚠️ 易混淆
① 是什么

瀑布式 Waterfall 是一种阶段串行的交付方式：需求、设计、开发、测试、上线依次进行， 前一阶段全部完成并交付文档之后，才进入下一阶段，像水从上一级台阶落到下一级，不回头。

本节把它单列出来，不是为了学它，而是因为 Agile、Lean、ITSM、安全文化以及 DevOps，都可以被读成对瀑布式交付某个缺陷的回应。 它是这一整章的共同对照系。

Waterfall 逐字列于 DOFD v3.4 官方考纲术语表（Concept and Terminology List，67 条），要求达到 Bloom 1–2，即认得并能理解。 v3.4 课程大纲的八个模块子项中没有出现 Waterfall，官方未指明这条术语归属哪个模块； 把它放在本章作为共同对照系，是本站的教学安排。
② 为什么存在 · 解决什么问题

瀑布式本身也是对痛点的回应：它出现之前，软件交付缺少阶段划分与文档纪律， 项目做到哪一步、谁负责什么、验收标准是什么，全靠口头约定。 瀑布式给出了明确的阶段、明确的交接物、明确的责任边界 —— 这在当年是进步。

它自己制造的痛点，才是后面所有框架的起点：

  • 某企业一个 18 个月的核心系统项目，需求在第 2 个月冻结、签字封存。 第 16 个月进入集成测试，第一次把各模块拼在一起， 发现三个模块对同一个字段的理解各不相同。
  • 此时距离需求冻结已经 14 个月：改一处要回溯设计文档、重排开发排期、 重签变更单。而业务侧在这 14 个月里早已换了打法， 最终上线的是一套按 14 个月前的业务假设造出来的系统。
  • 三个结构性缺陷同时出现：批量巨大（18 个月的变更一次交付）、 反馈滞后（集成与用户验证都堆在末端）、 变更昂贵（越晚发现，改动成本越高）。

本案例为本站构造的教学示例，用于说明阶段串行交付的失效机制，非真实调研数据。

后面每一个框架，都在拆这三条中的一条或几条： Agile 拆批量与反馈滞后，Lean 拆等待与浪费，ITSM 补上线之后无人负责的那一段， 安全文化拆「坏消息不敢说，所以问题一直藏到集成时才爆」这一层。 （这一因果归纳为本站教学整理。）

③ 与相邻概念的区别
维度WaterfallAgileDevOps
覆盖到哪一段 需求到上线，但每段之间是交接 需求到可工作的软件 需求到生产上稳定运行并产生反馈
批量 一次交付整个项目 一次交付一个迭代 一次交付一个变更，越小越好
反馈出现在哪 末端：集成测试与上线之后 每个迭代末 贯穿全程，含生产运行的遥测
与运维的关系 上线即交接，之后是别人的事 通常不覆盖运维 开发与运维同属一条价值流
它留给下一步的问题 批量大、反馈晚、变更贵 上线之后那一段没人管 —— 本章其余各节在补它的各个侧面

最容易混的一点：把 DevOps 当成「Agile 的升级版」。 这个说法把三者排成了一条替代链（瀑布 → 敏捷 → DevOps，后者淘汰前者），方向就错了。 正确的读法是覆盖范围不同：Agile 的终点是可工作的软件， DevOps 把这条线延长到生产运行与反馈，并且把 Agile 原样接了进来。

本三列对照表为本站教学整理，官方未以此形式给出瀑布、敏捷、DevOps 的对比； Waterfall 与 Agile software development 均逐字列于 DOFD v3.4 官方考纲术语表。

④ 工程中怎么用

实际工作里很少见到自称瀑布的团队，常见的是披着敏捷外衣的瀑布。 识别它不看仪式，看四个结构特征：

  • 需求仍然一次冻结：迭代计划做了，但整个季度的需求在第一个迭代前就全部锁定， 中途变更走「需求变更单」。迭代变成了排期单位，不是反馈单位。
  • 测试堆在最后：前六个迭代开发，后两个迭代「集中测试」。 这是把瀑布的阶段串行缩小了尺寸，缺陷结构完全没变。
  • 上线仍是一次性事件：每个迭代都有「潜在可交付的增量」，但一年只上线两次。 批量并没有变小，只是被藏在了迭代背后。
  • 交接物还是文档：迭代之间靠文档交接，跨职能团队名义上存在， 实际上开发、测试、运维仍按职能排队等待。

判据只有一句：看反馈到达的时刻有没有真的提前。 仪式全套但反馈仍然只在末端出现，那就仍然是瀑布。

这份「披着敏捷外衣的瀑布」四特征清单与识别判据为本站教学整理， 官方术语表收录 Waterfall，未给出识别标准或反模式清单。
⑤ 考试怎么考
  • Waterfall 主要作为对照系出现，很少单独成题。 典型形态是题干描述一个「阶段串行、反馈只在末端、变更成本高」的组织， 问应当引入什么，或问这体现了什么问题。
  • 考纲为 Bloom 1–2，要求认得与理解；瀑布模型的阶段数、提出年份与提出人 不在 67 条术语表与八个模块子项内。 （官方未公布题目层面的排除清单，此为本站教学提示。）
  • 干扰项长什么样： 把 Waterfall 描述成「已经被淘汰、不应存在」的选项 —— 措辞绝对化的通常不对； 以及把某个框架的贡献错配到瀑布的另一个缺陷上， 例如说「引入 Agile 是为了补上线之后无人负责的那一段」（那是 ITSM 与 DevOps 的位置，不是 Agile 的）。
  • 排除技巧：先在题干里找症状词 —— 「批量大 / 周期长 / 反馈晚」指向 Agile 与 Lean 那一侧； 「上线之后没人管 / 变更无记录 / 事件无响应」指向 ITSM 那一侧； 「不敢报告问题 / 频繁救火 / 大量单点故障」指向安全文化 （由 DOFD v3.4 官方样题答案键确认）。症状定位框架，是本章最通用的一把钥匙。

以上仅描述命题角度与干扰项构造方式， 不复制任何官方样题的题干与选项原文； 「症状定位框架」这一排除技巧为本站教学整理。 本章练习将提供仿真题（仿真题，非官方真题）。

⑥ 记忆要点

所有这些框架都在回答同一个问题：怎么不再像瀑布那样，把反馈留到最后。

瀑布留下三条缺陷，正好对应本章的分工： 批量大 → Lean 与 Agile；反馈晚 → Agile 与 DevOps；上线之后无人管 → ITSM 与 SRE。 记住这条分配表，「症状 → 框架」类的题就有了固定入口。（分配表为本站教学整理。）
