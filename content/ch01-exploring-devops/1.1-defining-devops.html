1.1 定义 DevOps

Defining DevOps
📘 官方模块子项 📌 高频 ⚠️ 易混淆

DevOps 这个词被用得太随意，以至于它几乎可以指任何东西 —— 一个岗位、一个部门、一堆流水线脚本。而官方 Blueprint 写下的那句定义里， 主语是「人」，谓语是「协同工作」，工具一个字都没提。 这一节要做的事只有两件：把那句官方定义拆开，再把六个最贵的误解逐个排除掉。

🎯 本节要回答
  • 这一节要拆的那句定义到底说了什么：谁、做什么、要同时达成哪几个结果
  • CALMS 五个字母各自代表什么，为什么它是定义的展开而不是另一套理论
  • DevOps 不是什么 —— 六个误解各自从哪来，以及它们分别让组织付出了什么代价

DevOps 的定义与名称由来Defining DevOps

⭐ 考纲核心📌 高频
① 是什么

DOFD 的官方 DevOps 定义写在 PeopleCert《DevOps Foundation® Blueprint》正文里，逐字原文是：

With DevOps, people across the IT organization, working together, enable fast flow, feedback and continuous improvement of planned work into production, while achieving quality, stability, reliability, availability, security and team satisfaction.

本站译文：借助 DevOps，IT 组织中的各方协同工作，使计划中的工作能够快速流动、 获得反馈并持续改进，直至进入生产环境，同时达成质量、稳定性、可靠性、可用性、 安全与团队满意度。

来源级别：上面的英文句为官方原文，出自 PeopleCert《DevOps Foundation® Blueprint》正文，可直接引为官方定义； 同一份 Blueprint 还以六个色块给出 CALMS 五值、The Three Ways、Organization、 Principles & Practices、Related Frameworks、Benefits。 DevOps 一词逐字列于 DOFD v3.4 官方考纲术语表。 中文为本站译文；下文对这句定义的拆解、推论与判题建议属于本站教学整理，已就地标注。

这句定义看着长，拆成三段就只剩三个词：谁 → 做什么 → 同时守住什么。

定义的三段官方定义句里的对应部分为什么这一段不能删
谁 IT 组织中的人协同工作
people working together		 主语是人不是工具。删掉这一段，DevOps 就退化成一次采购
做什么 计划中的工作快速流动、获得反馈、持续改进，直至进入生产 终点是「进入生产」而不是「开发完成」。这一段划定了范围，也正好是三步工作法的三个动词
同时守住什么 质量 · 稳定性 · 可靠性 · 可用性 · 安全 · 团队满意度 「同时」两个字是定义的重心：只快不稳不叫 DevOps。注意结果里包含人的满意度。 这六项的展开见 1.4 价值、目标与干系人

名称本身是合成词：Development ＋ Operations。 两个原本被组织分开考核的职能被写进同一个词里 —— 这个构词法本身就是定义的缩写版。

DevOps 一词逐字列于 DOFD v3.4 官方考纲术语表； 上表对「三段」的切分与「为什么不能删」的解释为本站教学整理。 「Development + Operations 合成词」这一构词说明同属本站教学补充，官方文件未对名称构成作专门定义。

② 为什么存在 · 解决什么问题

这个定义要解决的痛点非常具体：两个部门被同一个组织用互相冲突的指标考核， 于是理性地做出互相伤害的行为。

  • 某保险公司的保单系统，开发团队按「季度上线功能点数」考核，运维团队按「可用性 99.95%」考核。 开发想多上线，运维想少变更 —— 两边都在完成自己的 KPI。
  • 结果是发布窗口被压到每季度一次，每次上线 200 多个变更、6 小时窗口、周六夜里执行。 批量大到没人能说清是哪个变更引起的故障，回滚只能整包回滚。
  • 故障之后进入第二阶段：互相举证。运维出具「代码未通过压力测试」的证据， 开发出具「环境配置与测试环境不一致」的证据。会开了三次， 没有任何一条改进项落在两个部门的中间地带 —— 因为那块地没有主人。
  • 第三阶段是自我强化：既然上线这么痛，业务方就把需求攒起来一次提，批量进一步变大， 下一次发布更痛。这是一个会自己加速的循环。

官方定义句里的「IT 组织中的人协同工作」，针对的正是「没有主人的中间地带」； 而「同时达成质量、稳定性与安全」，针对的是「用速度换稳定或用稳定换速度」这种二选一的假设。 DevOps 的主张是：这两件事在同一套工作方式下可以一起变好，而不是零和。

本案例为本站构造的教学示例，用于说明冲突考核如何自我强化，数字非真实调研数据。

最容易混的一点：DevOps 与 ITSM 常被摆成对立面（「有了 DevOps 就不需要变更管理了」）。 这是错的方向 —— 两者关注的是同一条价值流的不同侧面。

与上表分开的一条官方事实 —— 官方样题答案键确认：对 DevOps 最关键的 ITSM 流程是组织变革管理、服务连续性管理、事件管理三者皆是 —— 即 ITSM 是 DevOps 的配合面而非替代对象。该结论由 DOFD v3.4 官方样题答案键确认，展开见第 4 章； 本站只陈述结论，不复制题干与选项原文。

④ 工程中怎么用

把这句官方定义当成验收标准用：任何一份写着「DevOps 改造」的方案，逐条对照三个问题。

  • 动的是人的协同方式吗？ 看方案里有没有改变交接方式、责任边界或考核口径。 如果通篇只有采购清单和岗位任命，那它动的不是定义里的主语。
  • 终点是不是「进入生产」？ 一个只覆盖到「测试通过」的流水线， 不缩短从想法到生产的总时间。用一个真实变更做端到端计时，比看流水线报表可靠。
  • 六个结果目标是不是被同时衡量？ 只报「部署频率涨了 5 倍」而不报变更失败率与恢复时间， 等于把官方定义里的「同时」删掉了。度量的完整口径见 第 7 章 度量、指标与报告。
  • 团队满意度算不算数？ 定义把它写进了结果目标。 如果部署频率靠加班和夜间发布堆出来，按定义那不算达成。

以上四个检查动作为本站教学整理：官方给出了定义句，但未规定任何验收方法。

⑤ 考试怎么考
  • 定义题（本站判断偏 Bloom 1）：直接问 DevOps 的定义或目标。 本站判断：正确选项通常同时含两个要素 —— 人的协同与「快速」和「质量／稳定性」并存； 少了任何一个，都与官方定义句对不上。
  • 干扰项长什么样 · 之一：只留速度。 写成「尽可能快地把变更推到生产」——听起来完全正确，但删掉了「同时达成质量、稳定性、可靠性、可用性、安全」。 凡是只谈速度的选项一律先划掉。
  • 干扰项长什么样 · 之二：换主语。 把主语从「人」换成「一套工具」「一个自动化平台」「一个团队」。 排除技巧（本站判断）：看主语 —— 官方定义句的主语是 IT 组织中的人。
  • 干扰项长什么样 · 之三：缩短终点。 把「直至进入生产」写成「直至开发完成」或「直至通过测试」。 这类选项通常是给 Agile 的定义换了个标签。
  • 范围题：问 DevOps 覆盖到哪里。本站判断：答案方向是到生产（官方定义句逐字写的是 into production）， 而不是到某个内部里程碑。

题型与 Bloom 层级的对应为本站教学推断，官方仅公布整体范围为 Bloom 1–2。 以上只描述命题角度与干扰项构造方式，不复制官方样题的题干与选项原文； 本面引号内的题干句式与选项示例均为本站自造，非官方样题选项原文。本章练习题均为仿真题，非官方真题。

⑥ 记忆要点

人协同 → 让计划中的工作快速流到生产 → 同时守住质量、稳定、可靠、可用、安全，还有人的满意度。

只记一个字也行：「同时」。DevOps 的全部难度都在这两个字上 —— 单要快或单要稳，早就有成熟做法了。

CALMS：定义的五个展开维度Culture · Automation · Lean · Measurement · Sharing

⭐ 考纲核心📌 高频
① 是什么

CALMS 是 DevOps 的五个价值维度， 官方 Blueprint 逐字给出：C: Culture / A: Automation / L: Lean / M: Measurement / S: Sharing。 本站把它当作前面那句官方定义的五个可以分别检查的面来用。

字母官方英文在官方定义句里对应哪一部分相关考纲术语（本站挂靠）
CCulture 「IT 组织中的人协同工作」—— 定义的主语 Organizational culture ⭐ 考纲核心
AAutomation 让工作「快速流动」的手段之一 DevOps toolchain · Continuous integration
LLean 「快速流动」的另一半：去掉不产生价值的等待与交接 Lean thinking · Waste · Value stream mapping
MMeasurement 「获得反馈并持续改进」的依据 DevOps metrics · Change lead time
SSharing 让改进从一个团队扩散到整个组织 Collaboration and communication ⭐ 考纲核心

五个字母及其英文全称出自 PeopleCert DevOps Foundation Blueprint，可引为官方； CALMS、Organizational culture、Collaboration and communication 三个词条均逐字列于 DOFD v3.4 官方考纲术语表。 右侧两列（「在官方定义句里对应哪一部分」与「相关考纲术语」）均为本站教学整理， 官方未给出 CALMS 字母与定义要点、与术语表条目之间的归属关系； 所列术语本身逐字见于 DOFD v3.4 官方考纲术语表，但把它们挂到某个字母下是本站做法。

② 为什么存在 · 解决什么问题

一句定义没法被执行，也没法被检查。CALMS 解决的是一个很实际的问题： 组织总会只挑自己最擅长的那一个字母做，然后宣布转型完成。

  • 某支付团队推行 DevOps 一年，成果是：单元测试覆盖率 82%、 持续集成每次提交 8 分钟出结果、全套容器化。A 这一项做得几乎无可挑剔。
  • 但变更前置时间从 47 天只降到 41 天。原因在别处：上线仍需三级审批，平均排队 26 天（L 没动）； 没人统计这 26 天在哪（M 没动）；团队之间互不知道对方踩过的坑，同一个配置错误在三个团队各犯一次（S 没动）。
  • 更贵的一项是 C：因为考核没变，运维依然为每次变更承担全部风险， 于是审批越审越严 —— 自动化越强，审批越紧，两者互相抵消。

CALMS 的作用就是把这种「单点突进」变成可见的：五个格子摆在一起， 空着的那几格一目了然。

本案例为本站构造的教学示例，数字用于说明「单字母突进」的失效机制，非真实调研数据。

④ 工程中怎么用

当五格体检表用，每格问一个不能靠感觉回答的问题：

  • C：上一次线上故障的复盘记录里，写的是「谁操作的」还是「哪个环节让这个操作变得容易出错」？
  • A：从代码提交到可部署产物，中间还有几个需要人手动点的步骤？数出来，不要估。
  • L：一个变更的总时长里，实际动手时间占几成？其余的等待发生在哪一环？
  • M：变更前置时间、部署频率、变更失败率、平均恢复时间 MTTR，这四个数现在能不能立刻报出来？
  • S：另一个团队上周踩的坑，这个团队知道吗？知道的渠道是什么 —— 文档、演练，还是口口相传？

五个体检问题为本站教学整理，官方只给出 CALMS 五个字母及其英文全称，未规定评估方法。

⑤ 考试怎么考
  • 字母展开题（本站判断偏 Bloom 1）：问 CALMS 每个字母代表什么。这是送分题， 但干扰项全部是近义词替换，必须逐字记官方英文。
  • 三个高危替换：L 是 Lean 不是 Learning； M 是 Measurement 不是 Monitoring / Metrics； S 是 Sharing 不是 Security / Sourcing。 这三个替换词在 DevOps 语境里都成立，所以特别难排除 —— 只能靠死记官方原词。
  • 归类题：给一个做法，问属于 CALMS 哪一维度。 排除技巧：先判断这个做法有没有涉及工具，没有工具的一律不是 A； 涉及「跨团队传播经验」的是 S 不是 C。
  • M 的边界题：度量的目的是改进系统，不是评价人。 官方样题答案键确认：用指标控制和评价员工不属于 DevOps 领导力的目标 —— 该结论由 DOFD v3.4 官方样题答案键确认，凡是把度量写成「考核个人绩效」的选项都可以直接排除。

题型与 Bloom 层级对应为本站教学推断。以上只描述命题角度与干扰项构造方式， 不复制官方样题的题干与选项原文。

⑥ 记忆要点

C 文化 · A 自动化 · L 精益 · M 度量 · S 分享 —— L 是 Lean 不是 Learning，S 是 Sharing 不是 Security。

结构记法：C 是主语，A 与 L 是让工作变快的两条路，M 提供依据，S 让改进离开单个团队。 五格里空得最久的那一格，通常就是转型卡住的地方。

DevOps 不是什么：六个误解What DevOps is not

📝 教学整理⚠️ 易混淆
① 是什么

前面那句官方定义用正面说法划出了 DevOps 的范围，但真正让组织走弯路的是它的反面。 六条否定式表述：DevOps 不是一套工具、不是一个岗位、 不是一个新部门、不是 NoOps、 不等于自动化、不等于 Agile。

这六条有一个共同结构：都在把「协同方式的改变」偷换成一件可以采购、可以任命、可以宣布完成的东西。 协同方式改起来慢、看不见、无法在季度汇报里展示 —— 所以每个误解都比真相更有吸引力。

「六个误解」的归纳与分类为本站教学整理， 官方 Blueprint 给出的是定义句与六个色块的正面表述，未以「DevOps 不是什么」的形式列出清单。 其中 NoOps 一词不在 DOFD v3.4 官方考纲的 66 条术语表内 🧭 延伸 · 非考纲，此处仅作为需要澄清的行业说法出现。

② 为什么存在 · 解决什么问题

这些误解不是学术分歧，每一条都有明确的账单。三个典型走法：

  • 成立「DevOps 部门」。 某零售企业从开发和运维各抽三人组建 12 人的 DevOps 部， 负责流水线与发布。半年后的实际效果是：原来开发与运维之间有一堵墙， 现在变成两堵 —— 开发把活扔给 DevOps 部，DevOps 部再扔给运维， 而且新增了一次排队。设部门解决的是「归谁管」，而定义要解决的是「谁和谁一起干」。
  • 招「DevOps 工程师」。 岗位描述写的是流水线、容器、脚本。 入职三个月后此人成为全公司唯一懂发布流程的人 —— 一个新的单点故障。 考核口径没变、责任边界没变，唯一的变化是把跨部门协作压缩成了一个人的待办清单。
  • 上工具链。 采购完成，看板、流水线、监控大屏齐备， 变更前置时间从 47 天变成 44 天。因为占大头的 26 天审批排队不在任何一个工具的范围内 —— 工具能压缩「动手时间」，压缩不了「等人批准的时间」。

这三笔账的共同点是：钱都花在了看得见的那一半， 而官方定义里的「人协同工作」始终没有被触碰。

三个案例均为本站构造的教学示例，用于说明误解的代价机制，非真实调研数据。

③ 与相邻概念的区别
被拿来替代 DevOps 的说法这个误解为什么会产生实际是什么 · 与 DevOps 的边界在哪
不是一套工具 工具是唯一可以立刻采购、立刻演示、立刻写进汇报的部分；厂商也乐于把产品称作「DevOps 平台」 工具属于 CALMS 的 A，是五分之一。官方定义句里没有出现任何工具
不是一个岗位 招聘网站需要一个可检索的职位名；「DevOps 工程师」比「改变协作方式的人」好写得多 DevOps 是整个组织的工作方式。把它压给一个岗位，等于制造新的单点故障。 角色的三个切面见本章 1.4 价值、目标与干系人， 组织设计见 第 8 章 分享、跟随与演进
不是一个新部门 组织解决跨部门问题的默认手段就是再设一个部门，并给它一个负责人 新部门增加一堵墙和一次交接，与「让工作快速流动」的目标直接相反
不是 NoOps 🧭 延伸 · 非考纲
不在 DOFD v3.4 的 66 条术语表内		 「开发能自助上线」被读成「不再需要运维」；云与托管服务加深了这个印象 运维工作没有消失，只是形态改变：从手工执行变成建平台、定标准、保障可靠性
不等于自动化 自动化见效快、可量化，是转型里最容易证明自己在推进的事 自动化放大现有流程：流程是对的，它让好结果更快；流程是错的，它让错误更快、更多
不等于 Agile 两者都讲小批量、快速交付、迭代反馈，词汇高度重叠 范围不同：Agile 的重心在把软件做出来，DevOps 的终点是进入生产并稳定运行。 Agile Manifesto 逐字列于 DOFD v3.4 官方考纲术语表；相关内容见 第 4 章 业务与技术框架

最容易混的一点：「DevOps 等于自动化」。 它比其他五条更难识破，因为自动化确实是 DevOps 的组成部分 —— 错的不是内容，是「等于」。判据很简单： 自动化只覆盖 CALMS 的 A，一个把审批排队、考核冲突原封不动保留下来的组织， 自动化做得再好，官方定义里的六个结果目标也不会同时改善。

本对照表为本站教学整理，官方未以「误解 — 成因 — 实际」的形式给出对照。

④ 工程中怎么用

拿到一份 DevOps 转型方案时，用四个动作快速判断它踩了哪条误解：

  • 数交接次数。 方案实施后，一个变更从提交到生产要经过几次「换人接手」？ 次数不减反增，说明加的是部门或岗位，不是协同。
  • 翻考核表。 开发与运维的考核指标有没有出现共同项？ 一条都没有，那么无论上多少工具，两边的行为动机仍然相反。
  • 问排队时间归谁。 变更前置时间里占比最大的那段等待， 方案里有没有明确的责任人？没有，就是典型的「买工具绕开难题」。
  • 看谁按下上线按钮。 如果全公司只有一两个人能完成发布， 那不是 DevOps，是把跨部门风险浓缩到了个人身上。

四个判断动作为本站教学整理，官方未规定此类评估清单。

⑤ 考试怎么考
  • 反向题（最常见）：「以下哪一项不属于 DevOps / 不是 DevOps 的目标」。 排除技巧：先找那个把 DevOps 缩成一件具体交付物的选项 —— 一个工具、一个岗位、一个团队、一次自动化改造，通常就是答案。
  • 干扰项长什么样 · 之一：正确但不完整。 「DevOps 是一组自动化实践」——内容没错，范围塌了。 凡是把 DevOps 限定在 CALMS 单个字母上的选项都要排除。
  • 干扰项长什么样 · 之二：组织结构式答案。 「建立一个专职 DevOps 团队」这类选项在成功因素题、领导力题里反复出现， 读起来像标准答案，但方向是错的。
  • 成功因素题：官方样题答案键确认， DevOps 的关键成功因素是管理层对文化变革的承诺 —— 该结论由 DOFD v3.4 官方样题答案键确认。 这一条直接否掉了「买工具 / 设部门 / 招人」三类选项：看到「文化」和「管理层承诺」优先考虑。
  • 选择依据题：官方样题答案键确认， 决定哪些 DevOps 原则与实践对组织最有益的是业务战略与目标 —— 该结论由 DOFD v3.4 官方样题答案键确认。 换言之不存在一份人人照抄的工具清单；这条的展开见本章 1.3 商业视角与 IT 视角。

题型判断为本站教学推断；以上只陈述官方答案键确认的结论与命题角度， 不复制任何官方样题的题干与选项原文。本面引号内的题干句式与选项示例均为本站自造， 用于演示干扰项的构造方式，非官方样题选项原文。本章练习题均为仿真题，非官方真题。

⑥ 记忆要点

工具能买、岗位能招、部门能设 —— 唯独协同方式必须改，改不动的那部分才是 DevOps。

考场用的一句话：凡是把 DevOps 说成「一个东西」的选项，先划掉。 它是一种工作方式，不是一件可交付物。
