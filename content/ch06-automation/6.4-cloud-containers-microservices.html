6.4 云、容器与微服务

Cloud, Containers, and Microservices
📘 官方模块子项 ⚠️ 易混淆

这三个词经常被当成同一件事的三种说法，其实它们各自拆掉的是一堵不同的墙： 云拆掉「等环境」，容器拆掉「环境不一样」，微服务拆掉「等别人一起发布」。 三层各拆一堵墙，越往上越依赖下层已经打好的地基 —— 不是技术上必须，而是缺了下层收益会被抵消：没有云的弹性容量，容器的「随用随起」仍要排队等机器； 没有容器的环境一致性，微服务只会让部署对象从 1 个变成 40 个。 而最上面那一层要付的账，是把单体内部的函数调用换成了网络调用。

🎯 本节要回答
  • 云、容器、微服务分别消除了哪一个具体约束，为什么顺序颠倒过来收益会被抵消
  • 微服务的真正意义为什么是组织层面的——它买到的是「不用等别人就能发布」
  • 把函数调用变成网络调用之后，新增的代价有哪些；什么时候不该上微服务
kp-6-4-1

云与容器：把环境从约束变成参数Cloud & Containers

📘 官方模块子项
① 是什么

云 Cloud 是按需自助获取计算、存储与网络资源的方式：不需要提前采购，用多少付多少，不用了立刻释放。

容器 Containers 是把应用连同它的全部运行依赖打包成一个可移植镜像的方式： 同一个镜像在任何支持容器的机器上启动，得到的运行环境完全相同，启动时间以秒计。

本节涉及的官方术语表条目本站释义
Containers ⭐ 考纲核心 把应用与其依赖打包在一起、共享宿主机内核、可秒级启停的标准化运行单元
Microservices ⭐ 考纲核心 把应用拆成一组小而自治、可独立部署、通过 API 通信的服务（见 kp-6-4-2）
Open source ⭐ 考纲核心 源代码公开、允许自由使用与修改的软件。云原生这一层的运行时、编排、构建工具绝大多数是开源的
Application Programming Interface (API) ⭐ 考纲核心 系统之间约定好的调用契约：只暴露能做什么，不暴露里面怎么做（见 kp-6-4-2）

四条均逐字列于 DOFD v3.4 官方考纲术语表（Concept and Terminology List）。 Cloud 一词本身不在这 66 条内，但 Cloud, Containers, and Microservices 是 v3.4 课程大纲 M6 模块的子项名，属官方模块构成。

② 为什么存在 · 解决什么问题

这两样东西解决的是价值流里最不体面的一段：纯等待。

  • 等环境：某企业内部系统要做一次性能压测，需要一套与生产同规格的环境。 流程是提工单 → 容量评审 → 采购 → 上架 → 装机 → 交付，历时 9 周。 代码早在第 1 周就写完了，剩下 8 周价值流上什么也没发生。
  • 环境不一样：等到环境交付，压测跑不起来。 测试环境是运维照着一份 2019 年的装机手册配的，生产是另一位同事三年前手工调的， 两边的中间件小版本、内核参数、时区都不同。排查这个差异又花了 5 天， 最后结论是「在我机器上是好的」。

云把第一段从 9 周压到分钟级：申请资源变成一次 API 调用。 容器把第二段直接删掉：各环境装的不是「按同一份手册配出来的机器」，而是同一个镜像本身。 差异没有被管理，是没有机会产生。

本案例为本站构造的教学示例，周期数字用于说明机制，非真实调研数据。 官方可引用的相关数据是：供应与部署时间下降最多 90% （DOFD v3.4 Course Description，与整体 IT 成本下降 15–25%、变更失败率下降 50–70% 并列给出）。

③ 与相邻概念的区别

先分清本节自己这两个词的分工：云回答「有没有机器」，容量按需可得； 容器回答「机器上跑的是不是同一个东西」，环境一致。 在自建机房里也可以用容器，在云上也可以完全不用容器 —— 两者互不蕴含。

对比对象云与容器它
虚拟机 Virtual Machine
🧭 延伸 · 非考纲		 容器共享宿主机内核，只打包应用与依赖，镜像小、启动以秒计 虚拟机自带一整套操作系统，启动以分钟计，镜像动辄数 GB
「容器是更轻的虚拟机」是个方便但不准确的说法，两者的隔离边界不在同一层

最容易混的一点：云和容器解决的不是同一个问题，却常被合起来叫「上云」。 把虚拟机整机搬到云上（俗称「搬迁」），拿到的只有第一层收益 —— 资源来得快了， 环境漂移一点没少，因为搬过去的还是那些手工配出来的机器。

本对照表为本站教学整理，表中仅 Containers 逐字列于 DOFD v3.4 官方考纲术语表； Cloud、Virtual Machine、Infrastructure as Code、Kubernetes 均未收录于 66 条。 其中 infrastructure-as-code 逐字写在 PeopleCert DevOps Foundation Blueprint 的 CALMS-A 描述句里 （“CI/CD toolchains, and infrastructure-as-code enable automation, consistency, velocity and fast recovery.”）， 属官方文件正文点名的内容，因此判「📘 官方模块子项」而非「🧭 延伸 · 非考纲」；官方未以此形式给出该对照。

④ 工程中怎么用
  • 让镜像成为唯一制品：测试、预发、生产装的是同一个镜像， 只换注入的配置。这正是本章 6.2 部署流水线 里「制品只构建一次」那条要求的落地方式 —— 容器让它从纪律变成了默认行为。
  • 把环境当耗材：每个待评审的分支自动起一套临时环境，合并后自动销毁。 这在按需容量之前是不敢想的，因为一套环境要占一台长期存在的机器。
  • 用开源看住供应链：开源 Open source 让这一层的准入门槛几乎降到零，但镜像里打进去的每一个开源组件都是你的依赖，也是你的攻击面。 把依赖扫描放进流水线，属于 第 3 章 DevSecOps（3.5）的范围。
  • 先量「等待」，再决定投入：如果一套环境两小时就能拿到， 把云的弹性再调一倍并不会缩短端到端交付时间。先确认「等环境」真的是当前约束， 判断方法见第 2 章 约束理论（2.3）。

以上四条工程做法为本站教学整理，官方文件把 Cloud, Containers, and Microservices 列为 M6 模块子项，未规定具体实施清单。

⑤ 考试怎么考
  • 主要命题角度：术语识别。Containers 与 Open source 都是官方术语表条目，Bloom 1–2 的考法就是「给一段描述，问它是哪个词」或「这个词的正确描述是哪一项」。 容器的关键描述词是「打包应用与依赖」「可移植 / 一致」「轻量 / 共享内核」。
  • 干扰项长什么样（一）：把容器说成 「自带完整操作系统的轻量虚拟机」。 这句话前半截听着对，「自带操作系统」是虚拟机的特征，一出现就可以划掉。
  • 干扰项长什么样（二）：把 Open source 说成 「免费，因此不需要许可与安全管理」。开源指的是源代码可获取、可修改， 与「免费」和「免责」都不是一回事。选项里出现「因为免费所以…」的因果句，基本都是干扰项。
  • 干扰项长什么样（三）：把云的收益写成 「消除了对基础设施的管理需要」。云改变的是获取方式， 不是让基础设施消失。凡是把某项实践描述成「从此不再需要 X」的绝对句，先怀疑。
  • 排除技巧：这一组题的正确项几乎都在讲「一致性」与「按需」； 干扰项则倾向于讲「更快」「更便宜」「不再需要」。快和省是结果，不是定义。

官方未公布命题规律与题型分布，以上命题角度、干扰项构造与排除技巧均为本站教学推断； 官方仅公布考试范围为 Bloom 1–2。以上不复制任何官方样题的题干与选项原文。

⑥ 记忆要点

云给你机器，容器保证每台机器上跑的是同一个东西。

一句话推论：只上云不用容器，等待变短了但漂移还在； 只用容器不上云，环境一致了但仍然要排队等机器。两个约束要分别拆。

kp-6-4-2

微服务与 API：买到的是「不用等别人」Microservices & API

⭐ 考纲核心 📌 高频
① 是什么

微服务 Microservices 是一种架构风格：把一个应用拆成一组小而自治的服务， 每个服务围绕一项业务能力构建，可以独立构建、独立部署、独立回滚， 服务之间只通过明确定义的 应用程序接口 Application Programming Interface / API 通信。

三个不能少的限定词去掉它会变成什么
围绕业务能力去掉它，拆出来的是「前端服务 / 后端服务 / 数据库服务」这种按技术分层的切法 —— 加一个字段仍然要三个组一起改
可独立部署去掉它，就只是拆成了多个模块然后一起发布，付了分布式的代价却没拿到收益
只经 API 通信去掉它（比如两个服务共用一张数据库表），边界就是假的 —— 改表结构又变回全员协调

Microservices 与 Application Programming Interface (API) 均逐字列于 DOFD v3.4 官方考纲术语表； 上表「三个限定词」的拆解为本站教学整理。

② 为什么存在 · 解决什么问题

微服务解决的痛点，发生在会议室里，不在服务器上。

  • 某支付平台的单体系统，40 名工程师分 6 个小组共用一个代码库、一条发布火车。 客服提了个两行代码的文案修正，走完流程用了 17 天： 等下一个双周发布窗口（9 天）、等 6 个组的回归测试全绿（5 天）、等发布评审（3 天）。
  • 更贵的是连坐：某次发布因为营销模块的一个空指针整体回滚， 同一批车上另外 5 个组毫无关系的变更也被一起退了回来，下个窗口重来。 于是各组学会了「反正要等，那就多攒一点一起上」—— 批量越攒越大。
  • 把这 6 个域拆成独立部署的服务之后，文案修正当天就上了生产。 变的不是代码质量，是「一次发布要协调多少人」。

所以微服务的意义是组织层面的：它让一个团队不必与全体协调即可发布。 这正是第 2 章 第一步 · 流动（2.2） 要的东西 —— 缩小批量、缩短端到端交付时间，靠的不是让每个人打字更快，而是拆掉「一起发布」这个同步点。

本案例为本站构造的教学示例，人数与天数用于说明机制，非真实调研数据。

③ 与相邻概念的区别
对比对象微服务它
松耦合架构
🧭 延伸 · 非考纲		 是一种手段：用进程与网络边界强制解耦 是要达成的目标属性：改一处不牵动其他处、发一处不必等其他处
真正带来收益的是松耦合与独立部署能力。模块化良好的单体同样可以很松耦合，微服务只是达成它的一条路
单体 Monolith 部署单元有很多个，各自独立发布 部署单元只有一个，任何改动都要整体发布
单体不等于「没有模块」，它可以内部结构清晰，只是不能分开发
容器 Containers 是架构决策：系统被切成几块、边界画在哪 是打包与运行方式
单体可以装进一个容器；微服务也可以不用容器直接跑。两者常同时出现，但不是同一件事
API 是被切分出来的服务本身 是服务之间的契约：只承诺「能做什么」，不暴露「里面怎么做」
API 稳定，双方就能各自演进；API 一变，独立部署的前提立刻失效
康威定律 Conway's Law
🧭 延伸 · 非考纲		 是架构侧的切分 指出系统结构会趋同于组织沟通结构：架构边界与团队边界互相决定
推论：6 个组共管 1 个部署单元时，架构自然会长成单体。不在 DOFD 66 条术语表内，组织形态的展开见第 5 章 运营模型（5.5）

最容易混的一点：把「微服务」本身当成目标。 官方术语表收录的是 Microservices 这个词，但让端到端交付时间下降的从来不是服务的数量， 而是「一次发布需要协调多少人」这个数字变成了 1。 如果拆完之后 40 个服务仍然一起发版，那只是把一个单体拆成了 40 份的分布式单体 —— 代价全付了，收益一分没拿。

「微服务是手段、松耦合与独立部署能力是目标」这一区分，以及「分布式单体」这一说法， 均为本站教学整理；官方术语表列出 Microservices 与 API， 未收录 Monolith、松耦合、康威定律等词，也未以此形式给出该对照。

④ 工程中怎么用
  • 用一个问题验收拆分：这个服务能不能在不通知任何其他团队的前提下， 今天单独发布并单独回滚？答不上「能」，这次拆分就没有兑现收益，只兑现了代价。
  • 边界按业务能力画，不按技术分层画：「订单」「计价」「风控」是能力； 「Web 层」「服务层」「数据层」是分层。按分层拆，加一个字段还是要三个组一起动。
  • 一个服务一份数据：两个服务共用一张表，等于用数据库把它们又焊死了。 数据共享要走 API，不走表。
  • API 要有兼容期：新增字段可以随时发，删改字段必须先并行支持新旧两版， 等调用方全部迁完再下线旧版。没有兼容期的 API，就没有独立部署。
  • 先看组织，再看架构：一个服务由多个团队共同拥有，等于把跨组同步点从发布环节挪到了代码环节。 服务与团队的归属关系不清楚时，先别拆。
  • 把重复的运维负担收成平台：40 个服务各自搭一套构建、部署、监控， 认知负荷会压垮业务团队。这正是第 3 章 平台工程（3.10） 要解决的问题。

以上六条实施判据为本站教学整理，官方文件把 Cloud, Containers, and Microservices 列为 M6 模块子项，未规定拆分方法或验收标准。

⑤ 考试怎么考
  • 主要命题角度：微服务的定义与收益。 正确项的关键词几乎必然包含「小而自治」「围绕业务能力」「可独立部署」「通过 API 通信」 中的一到两个。看到「独立部署」，方向基本就定了。
  • 干扰项长什么样（一）：「微服务降低了系统的整体复杂度」。 这是本节最需要防的一句 —— 它读起来很顺，但方向是反的： 微服务把复杂度从代码内部搬到了服务之间，总量不降反升（见 kp-6-4-3）。
  • 干扰项长什么样（二）：「服务拆得越小越好」。 micro 指的是自治的粒度，不是尺寸竞赛（本站释义 —— 官方术语表只列词条、不附定义）。 凡是「越…越好」的绝对句都可疑。
  • 干扰项长什么样（三）：把微服务与容器划等号， 或说「采用容器即实现了微服务」。两者常同时出现，但一个是架构决策、一个是打包方式。
  • API 的考法：正确描述强调「定义好的接口 / 契约」「隐藏内部实现」； 干扰项常把 API 说成「一种编程语言」「一个数据库连接」或「一份用户手册」。
  • 排除技巧：这一组题的正确项讲的是「自治 / 独立 / 契约」； 干扰项讲的是「更简单 / 更小 / 更省 / 就是某个工具」。 凡是把架构风格等同于某个具体工具的选项，先划掉。

DOFD v3.4 官方样题答案键中没有直接涉及本节主题的条目， 因此本面不引用任何「官方样题确认」的结论。官方也未公布命题规律与题型分布， 以上命题角度、干扰项构造与排除技巧均为本站教学推断；官方仅公布考试范围为 Bloom 1–2。 以上不复制任何官方样题的题干与选项原文。

⑥ 记忆要点

微服务买到的不是「更小的代码」，是「不用等别人就能发布」。

配套的一句反问：拆完之后，一次发布还需要协调几个团队？ 答案不是 1，就说明边界画错了 —— 服务数量增加了，同步点一个也没少。

kp-6-4-3

代价与取舍：什么时候不该上微服务Microservices Trade-offs

📝 教学整理 ⚠️ 易混淆
① 是什么

拆成微服务，本质上是把单体内部的一次函数调用，换成了一次网络调用。 这一换，就把分布式系统的全部固有难题一并买了进来： 调用会超时、会失败、会重复；一个事务变成跨服务的一致性问题；一次报错要跨若干服务追链路。

这不是「实施不当」造成的，而是选择这条路必然附带的账单。 它不会因为技术更好而消失，只会因为工具更好而变得可以承受。

Microservices 是 DOFD v3.4 官方考纲术语表条目， Cloud, Containers, and Microservices 是 v3.4 课程大纲 M6 模块子项。 但「微服务的代价清单」与本知识点的全部取舍判据，是本站教学整理 —— 官方文件把这三者列为需要掌握的概念，未讨论其适用条件与副作用。
② 为什么存在 · 解决什么问题

这一面要解决的痛点，出现在拆分成功之后：发布确实变快了， 但「出了事没人说得清是哪儿」成了新常态。

  • 网络会失败：某电商的下单链路跨 7 个服务。促销当晚下单成功率跌到 88%， 各服务自己的健康检查全部是绿的 —— 因为每个服务只知道自己没崩， 不知道自己调下游时超时重试了三次。排查用了 3 小时 20 分， 最后定位在第 5 跳的一个连接池配置。
    在单体里，这段逻辑本来是一次函数调用，根本不存在超时这种失败模式。
  • 数据一致性从「免费」变成「要设计」：单体里「扣库存 + 建订单」是一个数据库事务， 要么全成要么全不成。拆开之后这变成两次跨服务调用， 第二次失败时第一次已经生效了 —— 必须自己设计补偿或对账。
  • 调试跨越了进程边界：单体里一个堆栈就能看到全貌； 微服务里同一个请求的痕迹散在 7 份日志里，没有贯穿全链路的标识就拼不起来。

这就是可观测性成为刚需而不是加分项的原因： 单体时代「看日志」够用，微服务时代不够。 展开见第 3 章 监控与可观测性（3.8）。

本案例为本站构造的教学示例，服务跳数、成功率与排查耗时用于说明机制，非真实调研数据。

③ 与相邻概念的区别
维度单体内的函数调用微服务间的网络调用
失败模式 要么正常返回，要么抛异常。没有第三种 还有超时、部分成功、重复投递、下游雪崩。「不知道成没成」是常态
延迟 纳秒级，可以忽略不计 毫秒级且抖动。链路一长，尾延迟按跳数累积
数据一致性 一个数据库事务解决，免费 跨服务，需要自行设计补偿、幂等或对账。要写代码，也要写运维预案
调试 一个堆栈看到全貌 要跨服务串链路，没有可观测性等于摸黑
改接口的成本 编译器会告诉你哪里坏了，改完一起发 没有编译器兜底，要靠 API 兼容期与契约测试；发布顺序本身成了一个约束
换来了什么 — 独立部署：一个团队不必等其他团队就能上线

最容易混的一点：「微服务让系统更简单」。 恰恰相反 —— 单个服务的代码变简单了，系统的总复杂度上升了， 只是被搬到了服务之间，换来了可以独立发布的位置。 微服务是一笔交易，不是一次优化：用运行期的复杂度，换开发期与发布期的自治。

本对照表与「这是一笔交易而非优化」的判断为本站教学整理，官方未以此形式给出该对照。

④ 工程中怎么用

先判断这笔交易划不划算。以下四种情况，微服务的协调成本高于收益：

  • 团队规模小：一共 8 个人、一个团队。「不用等别人发布」这个收益本来就不存在， 因为根本没有别人。拆完只剩代价。
  • 领域边界还没稳定：新业务前期，边界每两个月就要重画一次。 在单体里挪一个模块是一次重构，在微服务里挪一次边界是一场跨服务的数据迁移。 边界没想清楚之前，单体里改边界便宜得多。
  • 缺可观测性与部署自动化：还在手工部署、只有零散日志时拆成 20 个服务， 得到的是 20 份手工部署和 20 份看不懂的日志。先补下层，再动架构（见图 6-4-1）。
  • 约束根本不在这里：如果精益价值流口径下的前置时间大头是需求排期或审批 （该口径从需求被接受起算，含需求排队；DORA 口径的 Change lead time 从代码提交起算，不含这一段）， 拆服务一天也省不下来。先做约束理论（2.3） 意义上的定位，别对着非约束环节做优化。

更稳妥的次序（本站教学建议）：

  • 先做模块化单体：在一个部署单元内部把边界画清楚、把数据分开。 边界画对了，将来拆才便宜；边界画错了，先拆只会把错误固化成网络协议。
  • 按痛点逐个剥离：哪个模块最常改、最需要独立发布节奏，就先把哪个拿出来。 不要一次性重写。
  • 每剥离一个，验收一次：它能否独立发布并独立回滚？出事时能否在链路上定位到它？ 两个都答「能」，再剥下一个。
「四种不该上微服务的情形」与「模块化单体优先」的实施次序，均为本站教学整理， 官方文件未讨论微服务的适用条件，也未给出演进路径。
⑤ 考试怎么考
  • 主要命题角度：微服务带来的收益是什么。 正确方向永远指向「可独立部署 / 各团队自治 / 支持更频繁的小批量发布」， 也就是最终落回流动。
  • 干扰项长什么样（一）：「降低了系统整体复杂度」「减少了测试工作量」。 这两句都把代价说反了 —— 微服务增加的正是集成测试与运行期的复杂度。
  • 干扰项长什么样（二）：「消除了对监控的需要」 或类似的「从此不再需要 X」句式。方向恰好相反：微服务让可观测性更加必要。
  • 干扰项长什么样（三）：把三者的功劳互相张冠李戴 —— 说「容器实现了独立部署能力」或「微服务保证了环境一致性」。 各自的归属见图 6-4-1，一层对一堵墙，不要串。
  • 反向问法：问微服务不能带来什么，或采用微服务需要什么前提。 前者选「更简单 / 更省事」类；后者选与自动化部署、监控与可观测性、团队自治相关的项。
  • 排除技巧：这一组题里，凡是承诺「更简单」「更省」「不再需要」的选项， 几乎都是干扰项；承诺「更自治」「更快发布」「更小批量」的，几乎都是正确方向。

⑥ 记忆要点

微服务不让系统变简单，它把复杂度搬到能被独立发布的位置。

一句话代价：函数调用变成了网络调用 —— 于是有了超时、有了跨服务一致性、有了追链路，这就是可观测性从加分项变成刚需的原因。

不该拆的四种情形，按「人、边界、地基、约束」记： 人少（没有别人要等）· 边界不稳（挪一次要迁数据）· 地基没打（无自动化与可观测性）· 约束不在这（省不下时间）。
