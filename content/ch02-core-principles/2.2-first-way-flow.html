2.2 第一步：流动

1st Way: Continuous Flow
⭐ 考纲核心 📌 高频 ⚠️ 易混淆

第一步只有一个目标：让工作从开发流向运维、再流向客户的速度更快、更平稳。 它同时立了两条禁令，而这两条禁令正是考题最爱翻面写成干扰项的地方。 本节最后会收敛到一条因果链上 —— 所有实现流动的手段，最终都在做同一件事：把批量变小。

🎯 本节要回答
  • 第一步的目标到底怎么表述，为什么「让某个团队变高效」不算
  • 它明确反对的两件事是什么，各自会在下游造成什么后果
  • 为什么六类手段最后都指向同一件事 —— 缩小批量
kp-2-2-1

第一步的目标与两条禁令1st Way: Continuous Flow

⭐ 考纲核心📌 高频📝 教学整理
① 是什么

第一步的官方名称是 1st Way: Continuous Flow，中文全称 持续流动 Continuous Flow，本站固定简称第一步 · 流动，后文一律用「流动」。 它只有一个目标，方向是从左到右：

条目内容
目标 增加工作从开发 → 运维 → 客户的流动 flow from Dev → Ops → customer
禁令一 绝不把已知缺陷传递给下游
禁令二 绝不允许局部优化导致全局退化
官方事实包中可直接引用的只有 PeopleCert《DevOps Foundation® Blueprint》给出的名称 1st Way: Continuous Flow，以及 v3.4 官方考纲术语表条目 Flow。 上表把目标与两条禁令拆成条文的写法，出自 Gene Kim 等《The DevOps Handbook》对第一步的阐述， 经本站整理为便于记忆的条目形式；DOFD 官方考纲文件未以此形式逐条列出。

注意目标句里的三个落点：开发、运维、客户。少了「客户」这一端，就不是第一步， 而只是某个部门内部的效率提升。Flow 是 DOFD v3.4 官方考纲术语表中的条目。

② 为什么存在 · 解决什么问题

它针对的是两种在传统 IT 组织里被当作「正常操作」的行为。

场景一（禁令一被违反）：功能在测试环境暴露了一个偶发报错， 但发布窗口只剩两天，会上决定「记为已知问题，先上线，下个迭代修」。 上线第三周，这个偶发报错在生产环境变成每天二十次告警， 运维值班的人不知道背景，每次都从零开始排查；等真要修的时候，写代码的人已经在做别的项目了。 一个在开发环节花两小时能修的东西，在下游花掉了几十个人时。

场景二（禁令二被违反）：测试团队的考核指标是「用例执行数」， 于是他们要求需求攒够一批再送测，这样跑一轮回归最划算； 开发团队的考核指标是「迭代交付的故事点」，于是不断把没写完文档、没写完自动化测试的东西扔过墙。 两个团队的 KPI 都在变好，端到端交付时间却在变长。 没有第一步这条原则，没人有立场说这件事错在哪。

③ 与相邻概念的区别
对比对象第一步 · 流动它
局部效率 / 资源利用率 度量对象是工作：一个变更走完全程要多久 度量对象是人和机器：某个环节有多忙。忙不等于工作在流动
Velocity 速率 端到端的通过速度，终点是客户 敏捷团队在一个迭代内的产能估算，终点是「开发完成」
「零缺陷」 反对的是已知缺陷继续往下走，未知缺陷靠第二步的反馈去发现 要求上线前不存在任何缺陷 —— 这不是第一步的主张，也做不到
局部改进 允许，只要不让全局变慢；改进要在整条价值流上算总账 局部优化指的是以全局退化为代价的局部好看，这才是被禁止的

最容易混的一点：「局部优化」不等于「在局部做改进」。禁令二禁止的是「牺牲整体换局部指标」，不是禁止团队改进自己的环节。考题会用「团队优化了自己的构建脚本」这类无害的局部改进来诱导你误判。

④ 工程中怎么用

把这两条禁令当成会议上的判断工具：

  • 有人提「先上线，缺陷记到 backlog 里」 —— 直接命中禁令一。 反问一句：这个缺陷在下游被谁承担、成本放大多少倍？
  • 有人拿「我们组的工单闭环率提升了 30%」邀功 —— 先问 端到端的变更前置时间变了吗。没变或变长，就是禁令二。
  • 看到有人把「提高环节资源利用率」写进改进目标 —— 这是个危险信号。 环节越接近满负荷，队列越长、等待时间涨得越快。 （利用率与排队时间的非线性关系来自排队论，属本站教学补充，不在 DOFD 考纲术语表内。）
  • 评审任何改进提案，只认一个问题：它缩短的是端到端时间，还是只让某段更忙？
⑤ 考试怎么考
  • 命题角度一 · 直接问目标：题干问第一步/流动的目标是什么。 正确方向必须同时含有方向（从开发到运维到客户）和动词（增加流动 / 加快）。
  • 命题角度二 · 反向题：问第一步不包含 / 反对哪一项， 此时两条禁令的正面写法反而是正确答案。读清题干是问「是」还是「不是」。
  • 干扰项长什么样：出题人最省力的做法就是把两条禁令翻面写成正向选项—— 「允许已知缺陷向下游传递」「接受局部优化，即使整体交付变慢」； 另一类是把范围截短，只写到「加快开发团队的交付」而不提运维和客户； 还有一类是塞入第二步的内容，比如「缩短故障的平均恢复时间」。
  • 排除技巧：选项里出现「已知缺陷」+「下游 / 传递」， 或出现「局部」+「即使 / 尽管全局」这种让步句式的，在正向题里一律排除； 选项终点停在开发或运维、没有到客户的，也排除。

以上命题角度、干扰项形态与排除技巧，均为本站依据 Bloom 1–2 层级与公开学习目标所做的备考推断，官方未公布任何样题分析；本站不复制官方样题的题干与选项原文，本章练习提供的均为仿真题。

⑥ 记忆要点

向右流到客户为止；不把已知缺陷、也不把局部胜利留给下游。

目标记「开发 → 运维 → 客户」三个落点，禁令记「已知缺陷」「局部优化」两个词根，考场上够用。

实现流动的六类手段How flow is actually created

📝 教学整理⚠️ 易混淆
① 是什么

「增加流动」是原则，落到动作上是六类手段。它们不是六个并列选项， 而是互相支撑的一组：不可见就无法限制在制品，不限制在制品就压不下批量。

手段具体做什么直接效果
让工作可见把所有在制品放到一块看板上，包括计划外工作与运维工单先能看见队列，才谈得上管理队列
限制在制品 WIP给每个环节设在制品 Work in Progress / WIP 数量上限，满了就不许再接新活强迫「先做完再开新的」，队列变短
缩小批量把大需求拆成能独立走完全程的小块，提高交付频率等待、风险、定位难度同时下降
减少交接次数合并环节、组建跨职能团队、用自动化替代人工递交与签字每减一次换手，就减掉一段排队与一次信息损耗
持续识别并消除约束（详见 2.3 约束理论）找出限制整条价值流通过量的那一个环节，集中改它只有改约束才能提升整体通过量
消除价值流中的困境与浪费去掉不产生价值的等待、返工、审批、重复录入。浪费的官方分类见精益七种浪费 DOWNTIME Lean types of Waste，在 4.3 展开直接砍掉图 2-2-1 里那 85%
表中Flow、Constraint、Kanban、 Waste、Value stream mapping 均为 DOFD v3.4 官方考纲术语表条目； 但「六类手段」的清单与分类沿用 Gene Kim 等《The DevOps Handbook》对第一步技术实践的归纳 （其中「消除价值流中的困境与浪费」为该书章节标题 Eliminate Hardships and Waste in the Value Stream 的直译）， DOFD 官方考纲文件未以此形式列出，本站仅做中文整理与表格化。 其中「在制品 WIP」「批量 Batch size」本身不在 67 条术语表内，属理解用的补充概念。

「持续识别并消除约束」在本节只作为一条手段出现。约束理论 Theory of Constraints / ToC 的完整展开（怎么找、找到之后按什么顺序做）放在 2.3 约束理论。

② 为什么存在 · 解决什么问题

痛点是「增加流动」这句话本身无法执行 —— 会开完了，第二天没人知道要改什么， 于是采购一套 CI 工具就宣称做了 DevOps。

具体场景：一个二十人的团队，需求散落在邮件、Jira、企业微信群和几张私人待办清单里。 问「现在手上有多少活在做」，没人答得上来。每个人同时挂着五六件事， 每件都停在「就差一点」：等接口联调、等安全审批、等测试环境、等另一个组回消息。 周报上每个人都很忙，季度末真正交付到客户手里的只有三个功能。

这六类手段就是把「让它流起来」翻译成明天能动手的事： 先让它看得见 → 再让在制品变少 → 再让每一件变小 → 再让它少换几次手。

③ 与相邻概念的区别
手段它真正的含义常被误解成
让工作可见让队列和阻塞可见，目的是发现堵在哪让人的忙碌程度可见，变成向上汇报和绩效监控
限制在制品限制同时在制的数量，总量不变，只是排队等着减少要做的工作总量，或者「少接需求」
缩小批量缩小一次交付的规模，交付频率相应提高降低质量标准，或把需求拆成互相依赖、单独上不了线的碎片
减少交接减少换手次数，靠合并职责与自动化减少人手；或者只是把交接从邮件换成工单系统，次数没变
消除约束集中改那一个限制整体通过量的环节同时改所有看起来慢的环节 —— 资源被摊薄，整体不动
消除浪费去掉不产生价值的活动：等待、返工、多余审批削减成本、裁减人员

最容易混的一点：限制在制品 ≠ 少干活。它不减少总工作量，只改变「同时开着几件」。这是考题和实际推行时被反弹最多的一条。

④ 工程中怎么用
  • 先量再改：用价值流映射 Value Stream Mapping 把一个真实变更的全程画出来，每段标上处理时间和等待时间 —— 就是图 2-2-1 那张图的真实版本。 第一次画出来的结果通常会让人吃惊。
  • 数交接：数一个变更从提交到上线，经过多少个人、多少次审批签字、多少次「发个邮件通知对方」。 每一个数字都是一段可以被砍掉的排队。
  • 给看板列设上限：从当前平均在制品数打八折开始，满了就停止拉新卡、去帮忙清掉堵住的那张。 看板方法本身的机制（拉动、列设计、累积流图）在 3.7 展开，这里只用它的原理。
  • 拆到能独立上线：判据不是「工作量小」，而是这一块能不能自己走完全程并对客户产生价值。 拆完还必须五块一起上线的，等于没拆。
⑤ 考试怎么考
  • 命题角度：给一条具体做法，问它属于三步中的哪一步； 或者给四条做法，问哪一条不是用来改善流动的。
  • 干扰项长什么样：一类是「加资源」型 —— 加人、加班、增加并行项目数、 提高某环节的资源利用率；一类是「反向」型 —— 扩大批量以摊薄发布成本、 上线前增加一道人工审批以确保质量、同时启动多个改进项目； 还有一类是把第二步（2.4 反馈）的做法（监控告警与遥测、自动化测试反馈、问题出现即蜂拥解决、同行评审）放进流动的选项里， 以及第三步（2.5 持续改进）的做法（无指责事后复盘、混沌工程、改进型 Kata）。
  • 排除技巧：六类手段里，除了「让工作可见」， 其余五条的动词全是减少 / 缩小 / 消除。 所以看到选项写「增加并行工作」「增加审批」「扩大批量」， 基本可以直接划掉。这一条判据能解掉相当一部分流动题。
  • 「消除约束」服务于第一步的流动目标，不要因为它在 2.3 约束理论 单独成节就误判成另一步。 这一归属由 DOFD v3.4 官方样题答案键确认。

以上命题角度、干扰项形态与排除技巧，均为本站依据 Bloom 1–2 层级与公开学习目标所做的备考推断，官方未公布任何样题分析；本站不引用官方样题的题干与选项原文。

⑥ 记忆要点

看得见 → 变少 → 变小 → 少换手 → 找约束 → 去浪费。

六个动作里五个是「减法」，只有第一个是「加法」（增加可见性）。这个不对称本身就是排除干扰项的判据。

批量大小：为什么大批量是万恶之源Batch Size

📝 教学整理⚠️ 易混淆
① 是什么

批量 Batch Size 指一次流经价值流并交付出去的工作量。 大批量 = 攒够一批再一起送；小批量 = 做完一小块就送一小块。 总工作量不变，变的只是「切成几份、什么时候被验证」。 （「批量 / Batch size」不是 DOFD v3.4 官方考纲术语表中的 67 条术语之一，属理解流动所必需的教学补充概念；官方术语表中与之直接相关的是 Flow、Deployment frequency、Change lead time。）

② 为什么存在 · 解决什么问题

场景：一家公司季度发布，一次上线打包 300 个变更。 回归测试要跑两周，发布当晚出故障。这时候三件事同时发生：

  • 回滚代价太大：回滚意味着 300 个变更全部撤回，其中 299 个是好的、 而且好几个业务方等了三个月。于是没人敢回滚，只能凌晨在生产上热修。
  • 定位范围太大：嫌疑对象有 300 个，还互相耦合。查了六个小时才发现是其中一个配置项。
  • 结论被推向反方向：复盘会得出「发布太危险，要加强管控」， 于是发布周期从一季度拉长到半年，批量变成 600 个。下一次故障更难查。

这个自我强化的循环，是「大批量是万恶之源」这句话的全部含义： 它不只是慢，它会让组织做出让自己更慢的决定。

③ 与相邻概念的区别
对比对象批量 Batch Size它
部署频率 Deployment Frequency 量的是一次送多少 量的是多久送一次。两者互为倒数，缩小批量必然抬高频率
变更前置时间 Change Lead Time 是因：一次攒多少决定了要等多久 是被批量拉长的果，量的是单个变更走完全程的时间
在制品 WIP 是一次交付出去的量 是同时开着、还没交付的件数。限制在制品是压批量的手段，不是批量本身

最容易混的一点：小批量 ≠ 交付得少。总量不变，只是分次送；对客户而言拿到价值反而更早。

④ 工程中怎么用
  • 先数，再谈改进：数上一次发布包含多少个变更、多少个提交。 这个数字就是当前批量，也是最容易说服管理层的一个数字。
  • 回滚测试判据：问一句「现在要回滚，会连带撤掉几个不相关的变更？」 答案大于一，批量就偏大了。
  • 把发布和放开分离：代码可以小批量、频繁地上线，功能是否对用户可见由开关控制。 这样批量变小了，业务节奏不受影响。 （功能开关 / Feature Toggle 是本站的工程补充说明，不在 DOFD 考纲术语表内。）
  • 缩小批量是部署流水线 Deployment Pipeline 与 持续集成 Continuous Integration 存在的根本理由 —— 没有自动化，高频小批量在成本上不成立。这两者的机制在 第 3 章、 工具链层面在 第 6 章 展开，本节只点到关系。
⑤ 考试怎么考
  • 命题角度一：直接问缩小批量的好处，或问大批量带来什么问题。 答案方向是缩短等待、降低单次风险、便于定位，不是「节省成本」。
  • 命题角度二 · 场景题：描述一个季度发布、每次改动巨大、故障频发的组织， 问最该优先做什么。选缩小批量 / 提高发布频率一类， 不要选「加强发布前评审」「增加测试人力」。
  • 干扰项长什么样：最有迷惑性的一类披着财务和常识的外衣 —— 「大批量能摊薄每次发布的固定成本，因此更经济」「减少发布次数可以降低生产环境风险」 「批量越大越能保证版本一致性」。这些在日常直觉里都成立，在 DevOps 语境里全部是错的。 另一类是把小批量说成「降低需求质量」或「减少交付内容」。
  • 排除技巧：记住这条反直觉判据 —— 批量越小、单次发布覆盖的变更越少，单次风险越低； 发布频率提高是缩小批量的结果，不是原因。 所以凡是「减少发布次数以降低风险」「延长发布周期以保证稳定」的选项，一律排除。 （频率与稳定性正相关的实证来自 DORA / State of DevOps 报告，属本站教学补充，不在 DOFD 考纲术语表内。）

以上命题角度、干扰项形态与排除技巧，均为本站依据 Bloom 1–2 层级与公开学习目标所做的备考推断，官方未公布任何样题分析；本站不引用官方样题的题干与选项原文。

⑥ 记忆要点

批量越大：排队越久、风险越集中、定位越难、越不敢回滚。

四个「越」是一条因果链，不是四个并列好处的反面。链条的头是批量，所以缩小批量能同时改善四件事。

⭐ 一分钟回忆清单
  • 第一步的目标：增加工作从开发 → 运维 → 客户的流动。终点必须是客户
  • 两条禁令：不把已知缺陷传给下游；不允许局部优化导致全局退化
  • 局部优化（牺牲全局）被禁止，局部改进（不伤全局）不被禁止
  • 六类手段：可见 · 限制在制品 · 缩小批量 · 减少交接 · 消除约束 · 消除困境与浪费（消除约束的完整方法见 2.3 约束理论）
  • 手段里只有「可见」是加法，其余全是减法 —— 看到「增加并行 / 增加审批 / 扩大批量」直接排除
  • 因果链：批量越大 → 排队越久 → 风险越集中 → 定位越难 → 越不敢回滚
  • 反直觉判据：批量越小，单次风险越低，发布变频繁是结果不是原因；「减少发布次数以降低风险」永远是干扰项
