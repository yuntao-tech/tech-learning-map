## 四、六轮迭代的教训（避免重蹈覆辙）

**同一种事故发生了四次**：写作契约里写摘要而不是原文 → 校验 agent 按契约判定「无官方出处」→
作者删除或降级了**真实的官方内容**。

被误删过的包括：

| 被误删内容 | 真相 | 当时契约的缺陷 |
|---|---|---|
| Blueprint 官方定义句 | 逐字在 Blueprint 正文左侧 | §4.3 只列了六个色块名 |
| v3.4 三个量化收益百分比 | 逐字在 Course Description | §4 只收了模块大纲 |
| 「Concept and Terminology List」 | 官方逐字小节名 | §4.6 未给英文小节名 |
| CALMS 五格描述句 | 逐字在 Blueprint | §4.3 只列了五个字母名 |

另有一次**条数错误**：术语表实为 **67 条**，我从第一批起就写「66 条」，
一路继承六轮共 437 处引用，直到 A1 agent 逐条核对才发现。

**结论**：
1. **契约里放原文，不放摘要。** 任何官方文件，能逐字收录就逐字收录。
2. **§6.1 存疑上报、不删除** 是最后一道防线 —— 正是它保住了第 67 条术语。
3. **agent 上报的实质判断几乎每次都对**，错的是契约不完整。收到上报先回原始 PDF 核实，不要预设 agent 错。
4. **主控必须自己验，不能采信 agent 自述。** 有一次总编辑 agent 报告「样板节未改动」，
   实际它被改了两处 —— 靠 mtime 与 grep 才发现。这也是后来引入 git 的原因。

## 五、多 agent 工作流的有效结构

六轮下来稳定有效的结构：

```
写作契约（主控写，含全部官方原文）
   ↓
撰写（每节一个 agent，只能改自己那一个文件）
   ↓
双视角对抗校验（考纲准确性 / 一致性与技术质量，都要求「找错不是夸奖」）
   ↓
修订（允许驳回校验意见但必须写明理由）
   ↓
分章总编辑（跨节去重、术语统一、交叉引用、summary 对齐）
   ↓
主控独立核验（git diff + 机械审计脚本 + 抽读内容 + 浏览器渲染）
```

关键设计：

- **文件权限硬约束**：每个 agent 只能碰自己那一个文件。引入这条后越权改动归零。
- **两个校验视角必须分开且对抗**，合成一个会漏。
- **风格基准指向一个具体文件**（3.3），比抽象描述有效得多。
- **每批之前开分支，批次结束合并**，`git diff master` 是唯一可靠的核验手段。
- 网络故障会让 agent 批量失败（曾一次失败 41/65）。用 `resumeFromRunId` 重跑，
  已完成的从缓存回放，不浪费。
